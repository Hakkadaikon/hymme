# loopeng-tracecheck (spec と実装を実ログでつなぐ)

モデル検査が保証するのは「書いた spec」で、コードではない。命令型・並行のコードは手で抽象するので、spec と実装のずれが残る。
実システムが残した状態の列を spec に流し、「この観測はモデルの正当な振る舞いか」を機械に判定させると、そのずれを実データで確定できる。
1行ずつの不変条件チェック(`used <= Cap` を各行で確かめる)では見えない、**許されない遷移**(二重計上・取り消し・飛び越し)が見える。

**前提**: `tasks/loopeng/<Name>.tla` / `<Name>.cfg` が TLC を通っていること。無ければ **loopeng-modelcheck** へ戻る。実装が入った後の段なので、設計時の「対象コード無し」の台帳は対象を書き直しておく(手元に実装が無いときは「対象コード無し(実装後): 理由」。ゲートはそれ以外の「対象コード無し」を止める)。`tasks/verifiability/<Name>.md` の検証容易性の台帳が通っていること([`../verifiability/SKILL.md`](../verifiability/SKILL.md) の「強制のしくみ」)。

## 手順

1. **観測点を決める**: spec の変数のうち、実システムで観測できるものを選ぶ。全部でなくてよい(見えない変数は spec に選ばせる)。観測は「状態」で取る。イベント名ではなく、イベントの後の変数の値。
2. **ログを JSONL にする**: 1行 = 1観測状態、キーは spec の変数名。値は整数・文字列・真偽・配列(列)・オブジェクト(レコード)・`{"$set": [...]}`(集合)。浮動小数と null、制御文字を含む文字列は使えない(exit 2)。レコードのキーは TLA+ の識別子に限る。model value は扱えない。spec が `TC_` で始まる名前を使っていると生成モジュールと衝突する。
   同じ状態が続く行(記録はしたが観測値が変わっていない)は、spec の振る舞いが同じ状態を繰り返してよいので許される。
   ログの採り方を実装に足す必要があれば、配管側(ミドルウェア・テスト用フック)に置き、判定ロジックに混ぜない。
3. **回す**: `trace_check.py [--all] <Spec.tla> <run.jsonl> [--cfg <Spec.cfg>] [--timeout SEC]`。cfg の `CONSTANT` は自動で引き継ぐ(既定は spec の隣の `<Spec>.cfg`)。`CONSTRAINT`(探索を有限にするための上限)は引き継がない。TLC は既定 600 秒で打ち切る。
   - 全変数を毎行観測できる → `trace_check.py --all tasks/loopeng/<Name>.tla <run>.jsonl`。各ステップを独立に判定し、ずれを全件出す。行1が `Init` を満たすかも見る。
   - 一部の変数しか観測できない → `trace_check.py tasks/loopeng/<Name>.tla <run>.jsonl`。見えない変数は spec に選ばせ、最後の行まで届く振る舞いがあるかを判定する。報告は最初のずれ1件。
   - exit 0: ログ全体が spec の振る舞い。
   - exit 1: `不一致: N 行目は …` — その行への遷移を spec のどのアクションも説明できない。直前の行と並べて表示される。
   - exit 2: 判定できなかった。ログか spec の誤り(spec に無い変数名・JSON でない行・TLC のエラー)、TLC の時間切れ、`tlc` が PATH に無い、のどれか。
4. **ずれを判定する**: 出た行ごとに「実装の穴か、spec の書き漏れか」を決める。
   - 実装の穴: 失敗するシナリオ(loopeng-gherkin と同じ形)に固定してから実装を直す。
   - spec の書き漏れ(実装が正当に行う遷移を spec が知らない): 要件に戻って追記し、formalize → modelcheck をやり直す。spec を通すためだけに `Next` を緩めない。
   - 一部観測のモードは最初の1行しか報告しない。途中の行から切り出すと先頭行が `Init` を満たさず必ず不一致になるので、切り出しや spec の `Init` の書き換えで先へ進めない。1件ずつ直して再実行するか、全変数を観測したログを採って `--all` で全件を出す。
5. **並行の実装はアトミック版と素朴版を両方書く**: どちらの spec をログが満たすかで、実装が実際にどちらを実装しているかが確定する(read-modify-write が分離していれば素朴版だけが通る)。

## 出口条件

- 代表的な実ログ(正常系・高負荷・障害注入の各1本以上)が exit 0。
- 出た `不一致` は全件、実装修正か spec 修正のどちらかで閉じている。
- ログ採取の仕組みを本体に残すなら、配管側に置き、管理番号・手法用語を書かない([`../_shared/stealth-artifacts.md`](../_shared/stealth-artifacts.md))。

## やらないこと

- 1行ごとの不変条件チェックで代用しない。遷移の正しさは隣り合う2行を見ないと分からない。
- 長大なログを一度に流して TLC を待ち続けない(既定 600 秒で打ち切る。`--timeout` で変える)。観測する変数を増やして分岐を減らすか、全変数を観測して `--all` で回す。
- 実ログに秘密(トークン・個人情報)が入るなら、spec に不要な値はログを採る段で落とす。
