# review-feedback — レビュー指摘からの学習ワークフロー

## このスキルの目的

レビュー指摘をもらったら、指摘された箇所だけ直して終わるな。なぜ事前に見つけられなかったのかを考え、同種の問題を差分全体から探し、次回の検出手段のどこかにその観点を埋め込む。同じ種類の指摘を二度もらうのは、学習しなかったということだ。

トリガーはレビュー指摘に限らない。**再発しうる失敗を自分で起こした直後**(CI の赤を直した、バグの真因を特定した、運用手順の事故を回収した)も同じフローを実行し、**1回目で教訓化する**。過去の失敗ログを振り返ると、教訓の明文化は決まって同種の失敗を2〜3回繰り返した後に行われていた。2回目を待つ理由は無い。修正が終わった時点が埋め込みの時点だ。この場合は手順1の分類を「なぜ既存のゲート・チェックで防げなかったか」と読み替える。

## superpowers との分担

**REQUIRED SUB-SKILL:** 指摘の受け止め方(検証してから実装、追従語を書かない、不明点は先に確認、誤った指摘には反論する)は superpowers:receiving-code-review に従い、本スキルでは繰り返さない。本スキルが足すのは**受け止めた後**の 4 手順(分類・水平展開・埋め込み・記録)とコミット分割である。

**SDD の修正ラウンドでの分担**(superpowers:subagent-driven-development のタスクレビュー / 最終レビューの指摘を直すとき):

- 手順 1(分類)・手順 2(水平展開)・手順 5(コミット)は**修正を適用する側**が行う。SDD では implementer であり、コントローラは自分で直さない(SDD の規則)。implementer は水平展開の結果(同種箇所 or「他に該当なし」)を fix report に書く。
- 手順 3(埋め込み)・手順 4(lessons)は Task の範囲外なので、implementer は report に「埋め込み候補: <観点> → <候補先>」を 1 行書くだけにとどめる。SDD は最終レビュー後に workspace(report を含む)を `rm -rf` するので、コントローラは削除前に report から埋め込み候補を回収する。埋め込み先が対象リポジトリのテスト・Lint・PR テンプレートなら、最終レビューの fix 波の brief に含めて implementer に直させる(コントローラは自分で直さず、fix 波の後に未レビューのコミットを追加しない)。fix 波の後に出た候補と、hymme のレンズ基準(`skills/diff-review/references/`)や hook への埋め込みは、superpowers:finishing-a-development-branch の後の別タスク(別ブランチ / hymme リポジトリ側)として扱う。
- 手順 1 の「なぜ diff-review で見つけられなかったか」は、SDD では「なぜタスクレビュー(または前ラウンドの re-review)で見つけられなかったか」と読み替える。最終レビューで初めて出た指摘は「タスク単位レビューの視野外(横断)」か「基準の不備」かを分ける。

## ワークフロー

### 1. 指摘の分類

各指摘について、なぜ AI セルフレビュー(diff-review)で事前に見つけられなかったかを分析する。次のいずれかに分類する:

- **基準の不備**: 該当レンズはあったが、基準ファイルにその観点が無かった
- **レンズの不在**: どのレンズの担当領域にも入らない観点だった
- **レビュー未実施**: そもそも diff-review を実施していなかった
- **基準はあったが検出漏れ**: 基準に観点はあったのに指摘できなかった

この4分類は、レビューが見逃した理由である。テストの段で検出されなかった理由(要件の抜け、テストの書き漏れなどの6分類)は別の軸で、後段(結合・e2e・実ログ・CI・本番)で見つかった欠陥なら escape-flow スキルの欠陥の記録に書く。レビューでもテストでも検出されなかった失敗は、両方に分類する。

### 2. 水平展開

指摘された 1 箇所だけ直して終わらせない。同種の問題を差分全体、および変更対象の周辺コードから Grep / Read で探す。見つかれば同時に直し、見つからなければ「他に該当なし」を報告に書く。欠陥の記録を開いている失敗では、この結果を記録の「水平展開」の欄にも書く(空のままでは記録を閉じられない)。

### 3. 埋め込み

観点の再発防止先を最低 1 つ決めて反映する。候補:

- `skills/diff-review/references/` のレンズ基準ファイルへの観点追記
- hook(機械的にブロック・警告できる性質の観点)
- 対象リポジトリのテスト・Lint
- PR テンプレート・チェックリスト

どれにも該当しない一過性の指摘(そのコード固有・再現性なし)は埋め込みを見送ってよいが、その判断を報告に書く。

新しい検査(hook・Lint・テスト)を足すときは、**過去に実際に起きた失敗で止まることを示す**。今回の指摘の元になったコードか、それを再現した入力に検査を当て、落ちる出力を報告に貼る。落ちるのを見ていない検査は、何も守っていないかもしれない。既にコードベースに多く在る形を禁止する検査は、変更がその形を増やしたときだけ落とす(既存の全箇所で落とすと、誤って止まる回数が増えて検査ごと外される)。

検査に例外を置くときは、該当する行に**理由、期限、ユーザーの承認**の3つを付ける。hymme の統合の入口の検査は `hymme exception request <検査> --until YYYY-MM-DD --reason <理由>` で申請し、ユーザーが `承認 <承認コード>` と入力したときだけ外れる(期限は最長90日)。外せる検査は pr-create スキルの表に在る。閉じていない欠陥の記録と、ユーザーの確認(確認の一覧、状態遷移図)は外せない。理由だけの例外、期限の無い例外、本人が自分で認めた例外は置かない。

### 3.5 同じ抜けが2回出たら、構造で防ぐ

1回目の埋め込み(手順3)は変えない。ここで扱うのは、埋め込んだあとも同じ種類の抜けが繰り返された場合である。次のどちらかに当たったら、文面の追記で済ませず、構造で防ぐ手段を作る。

- `hymme escape stats` で、同じ「抜けた理由」が2回以上出ている(欠陥の記録 `tasks/escapes/` を理由ごとに数える。2回以上の行には印が付く)
- 規則が既に文面(スキル・レンズ基準・CLAUDE.md)に在るのに、強制の手段が無いまま2回破られた

指示の文を足しても、同じ文を読んだうえで2回抜けている。直す段を上から順に試し、使えた最も上の段で直す。

1. **設計で無くす**: 誤りが起こりえない形にする。状態の持ち主を1つにする、やり方を1つにする、手で同期している一覧を1つの源から作る、写されそうな古いやり方を消す
2. **型で書けなくする**: 不正な値や組み合わせをコンパイルか型検査で落とす
3. **Lint・hook・CI の検査で止める**: 落ちたときのメッセージに、使うべきファイル・型・関数の名前を書く。手元と CI で同じコマンドを実行する。手作業で誤った操作(置き換え、移行、点検)は、その操作を行うか、結果を確かめるスクリプトにする([`../_shared/scripted-work.md`](../_shared/scripted-work.md))
4. **テストで振る舞いを固定する**
5. **文書と agent 向けの規則**: 判断が要って上の段では扱えないものだけ。失敗の実例を添える

報告には、型ごとに、証拠(2回の出どころ)、選んだ段、より上の段が使えなかった理由を書く。誤りが起こりえなくなった規則は、文面から外す。

### 4. 記録

`tasks/lessons.md` へ教訓を 1 行追記する(指摘の種類・原因分類・埋め込み先)。

### 5. コミット

修正コミットは commit-flow の基準に従い、指摘単位で分ける。埋め込み(基準ファイル等の変更)は修正とは別コミットにする。

## 完了条件

報告に次の 4 点が揃っていること(SDD の implementer は 1・2 と「埋め込み候補」の 1 行、コントローラは 3・4):

1. 指摘の修正(該当コミット)
2. 水平展開の結果(見つけた同種箇所、または「他に該当なし」)
3. 埋め込み先(または見送り判断とその理由)
4. lessons への追記内容
