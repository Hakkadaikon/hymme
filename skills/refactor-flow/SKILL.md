# 振る舞いを変えない構造の変更

構造は変える。振る舞いは変えない。この2つを最後まで分けておくのが、この手順の役目である。

## 範囲を決める

- 作業の途中で、足りない機能やバグを見つけても、この変更には入れない。構造の変更を先に出し、機能は superpowers:brainstorming へ、バグは escape-flow へ渡す。
- 設計そのものを作り直すなら、それは新しい設計である。superpowers:brainstorming から始める。
- 検証のために判定を小さな関数へ切り出す作業は、[`../verifiability/SKILL.md`](../verifiability/SKILL.md) の手順で行う。振る舞いを固定する決まりは同じである。

## 手順

### 1. 先に振る舞いを固定する

構造を動かす前に、今の振る舞いを捉えるテストを書いて通す。使える形は3つある。

- 今の出力をそのまま期待値にするテスト(特性テスト)
- 出力を保存して比べるテスト(スナップショット)
- 古いコードと新しいコードに同じ入力を与えて、出力を比べるスクリプト

テストが無い領域では、構造に触る前に固定を書く。型検査と lint は固定にならない。振る舞いが変わっても通るからである。

### 2. 目標の形を決める

動かす前に、終わったときのモジュールの分け方、型、呼び出しの関係を書く。

- **足りない構造を名指しする。** 作り替えで、分岐か、起きてはならない状態が減ること。減らさずに間接の層だけが増える形は採らない。形が明らかで局所的なコードは、そのまま残す。
- **新しい要件を既存の設計に入れるときは、継ぎ足さない。** 「この要件が最初から前提だったら、どう作ったか」を問う。影響するファイルをすべて読んでから答える。
- **変更をすべての参照に行き渡らせる。** 型、文書、例、設計の理由を書いた節まで直す。コードだけ直して文書に古い設計が残ると、次の読み手が古い設計に従う。
- **全体の形を先に決め、届けるのは小さな単位にする。**
- 前例がコードベースに無い判断は、試作を2〜3個作って比べる([`../_shared/prototype.md`](../_shared/prototype.md))。

### 3. 先に削る

新しい形を入れる前に、次を消す。呼び出し元の無いコード、呼び出し元が1つだけのラッパー、重複した検証、どこからも参照されない定義。「役に立つかもしれない」だけの整理は、入れたあとで効果が示せなければ戻す。

### 4. 小さな歩で動かす

1歩ごとに、手順1の固定を通す。通らなくなった歩は、その場で戻して小さく分ける。

内部の API を作り替えるときは、同じ変更の中で呼び出し元をすべて移し、古い API を消す。互換のための層と、古い経路と新しい経路の並行は残さない。残すと、どちらを使うのが正しいかを読み手が判断できなくなる。

ただし、この決まりが当てはまるのは次の両方を満たすときだけである。

- リポジトリの外に、古い API に依存する利用者がいない。
- 呼び出し元を1回の変更で直しきれる。

満たさないとき(公開している API、ほかのリポジトリが呼ぶコマンド、古い形で保存されたデータ)は、互換を残す。残す理由と、消す条件を、コードのそばに書く。

テストは、新しい約束を確かめる形に直す。作り替える前の実装の細部だけを確かめていたテストは消す。アサーションを足した数より多く消すと、統合の入口の検査(`weaken`)が止める。消したテストごとの理由を示して、ユーザーに例外を申請する(`hymme exception request weaken`)。

### 5. 機械的な変更はスクリプトで行う

名前の置き換え、呼び出し方の書き換え、ファイルの移動のように、同じ操作を多くの箇所に当てる変更は、手で直さずスクリプトにする。2〜3か所の明らかな編集は手でよい。基準は回数ではなく、些細かどうかである。

1. 1か所目を手で直す。
2. その変更を行うスクリプトを書く。
3. 1か所目を元に戻し、スクリプトで直して、手で直した結果と同じになることを確かめる。
4. 全体に当てる。

- 何回実行しても同じ結果になるように書く。
- 目的を果たす最小のスクリプトにする。汎用の枠組みは作らない。
- スクリプトは、レビューする人が再実行できる場所に残す。作業がこのセッションで終わらないなら、コミットする。1回で終わる作業なら、PR の本文かコミットメッセージに載せる。
- 同じ編集を複数の subagent に配るより、決定的なスクリプト1本のほうが確実である([`../_shared/parallel-delegation.md`](../_shared/parallel-delegation.md))。

### 6. 名前の変更の漏れと取り違えを探す

置き換えは、目的の箇所を漏らすことと、変えてはいけない箇所を変えることの両方を起こす。置き換えたあと、実際のファイルで次を確かめる。

- **漏れを探す。** 古い名前を `git grep` で探し、残りが0件か、残すと決めたものだけであることを確かめる。漏れやすいのは、文字列の中、文書・コメント・メッセージの文、リンクと目次、設定と CI の定義、ほかのリポジトリからの参照である。
- **変えない名前を先に決める。** 保存済みのデータのパスや、ほかのツールが読む名前は、置き換えから外す。外す名前は、置き換える前に一覧にする。
- **外したはずの名前が、別の書き方で置き換わっていないかを探す。** 文字列をそのまま保護しても、パスを要素ごとに分けて書いたコード(`"tasks" / "loopeng"` のような形)は保護されない。置き換えたあとの差分から、新しい名前が単独で現れる行をすべて読む。
- **保存済みのデータに古い名前が残る場合を扱う。** 記録、設定、キャッシュが古い名前を持つなら、読む側で古い名前を新しい名前として読むか、データを移行する。古い名前のデータだけがある状態のテストを書く。
- **同じ名前を複数の箇所に手書きしていたら、1か所の定数にまとめる。** 次に名前を変えるとき、漏れなくなる。
- **利用者に見える名前を変えたら、古い名前と新しい名前の対応を文書に書く。**

### 7. 振る舞いが変わっていないことを示す

「コンパイルが通る」「型検査が通る」は証拠にならない。手順1の固定が、作り替えの前後で同じ結果になることを示す。大きな作り替えでは、次のどれかを足す。

- 古い出力と新しい出力を比べるスクリプト
- 記録しておいた基準を、新しいコードに与え直す
- 実システムを動かして確かめる(`hymme:real-surface` の確認のコマンド)

### 8. 残す価値を確かめる

作り替えの成果は、読み手の負荷が下がったかで測る。たどる層の数か、頭に置く可変の状態の数が、どこかで減っていること。どこも減っていなければ、その変更は戻す。

### 9. コミットを並べる

削除、作り替え、後片付けの順に、小さなコミットに分ける。どのコミットでも手順1の固定が通ること。粒度は `hymme:commit-flow`、実行は `hymme:micro-commit` に従う。

## 報告

次の5点を書く。新しい振る舞いは含めない。

- 変えた構造
- 固定に使ったテスト
- 振る舞いが変わっていない証拠(コマンドと終了コード)
- 読み手の負荷がどこで下がったか
- 入れた変更と、戻した変更
