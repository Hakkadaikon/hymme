# レンズ: 設計・可読性 (design)

このファイルは「何を見るか」と観点固有の severity 補正、報告末尾に付ける付記(影響の範囲)を定義する。
severity 体系・実害ベースの貫通原則・2 パス自己検証・確かさの段階は本体(diff-reviewer.md)に一元化されており、それをそのまま適用する。

## readable code(構造的問題のみ must)

以下の「読み手が誤読する・理解に不当なコストがかかる」構造的問題は must:

- 実態と合わない命名(名前が示す挙動と実装が食い違う)
- 深いネスト・追跡困難な制御フロー
- 多責務の巨大関数

読み手の負荷は2つの軸で見る。問いと答えのあいだにある層の数と、頭に置いておく隠れた可変の状態の数である。diff が増やした次のものは want+(現に追跡できなくなっていれば must)。

- **転送するだけの層**: 呼び出し元が1つのラッパー、2つ目の実装が無いアダプタ、引数をそのまま渡すだけのメソッド。層をなくせるならなくす
- **広すぎる状態の範囲**: 戻り値で足りるのに引数を書き換える、ローカルで足りるのにフィールドに置く、フィールドで足りるのにモジュールや大域に置く
- 目安の問い: 初見の読み手が「この値はどこから来るか」「何がこの値を変えうるか」に30秒で答えられるか

「もっと良い名前がある」「こう書く方が好み」レベルは want / nit。
**テストコードもこの基準の適用対象**。

## 関数型エッセンス(基本 want+)

- **副作用の分離**(中核): pure core / imperative shell。ロジックは純粋関数へ、I/O・状態変更は外側へ移す
- **イミュータビリティ**: 再代入・可変コレクション・引数破壊の回避
- **宣言的コレクション操作**: 手続き的ループより map / filter / fold 等の変換パイプライン
- **型によるエラー・不在表現**: null / 例外より Option / Result / sealed 型。ただしエラー戦略はプロジェクト規約が最優先
- **型で不正な状態を書けなくする**: 同時に成り立ってはならない組み合わせを持てる形(互いに同期が要る複数の真偽値、状態によっては無効になる任意フィールド)は、状態ごとの型(判別共用体・sealed 型・enum)に替える。同じ基本型で意味の違う値(ID と件数、秒とミリ秒)の取り違えが diff 内で現に起きているなら **must**
- **式指向・純粋関数の合成**: 基本 nit。関数型親和度の高い言語では want+ に引き上げ

### 適用強度の判定(2 段構え)

1. **言語の関数型親和度**(一次判定): Kotlin / Scala / Rust / TypeScript / Nix / Haskell / F# / Elixir 等は「強」= 上記の severity をそのまま適用し、式指向も want+ へ引き上げ。Go / C / shell / 手続き型レガシー等は「弱」= 一段下げる(want+ → want、nit は指摘しない)
2. **周辺コードの流儀**(補正): コードベースが徹底して命令型で書かれている場合は一段下げる。ただしゼロにはしない(改善方向への指摘は残す)

## SOLID / DRY / YAGNI(実害ベース)

違反が diff 内で実害として具体化しているもの(責務混在により現に変更が困難、コピペ重複が現にバグの原因、未使用の抽象が現に理解を妨げる)は must。違反はあるが実害が潜在的なら want。

- **DRY**: 「同一の知識・仕様が複数箇所に表現されている」場合のみ指摘する。偶然形が似ているだけのコード(incidental duplication)は指摘しない。重複 2 箇所は基本的に指摘せず、3 箇所目から原則指摘(rule of three)
- **YAGNI**: 原則同士が衝突したら YAGNI 優先。将来を推測した抽象・未使用の拡張点・使われないパラメータはむしろ YAGNI 違反として指摘する(誤った抽象は重複よりコストが高い)
- **先に削る**: 足す前に削れるものが diff に残っていないかを見る。置き換えたのに残した古い経路、呼び出し元の無くなったコード、仕様が求めていない推測の検証・パーサ・ガードは want+。古い経路と新しい経路が両方とも使える状態で、どちらが使われるかを読み手が判断できないなら **must**

## 境界と領域のモデル

- **境界で検証する**: 検証、型の絞り込み、エラー処理は、データが外との境界(CLI の引数、設定ファイル、外部 API、ネットワーク、DB の行)を越える場所で1回だけ行う。内側では型を信じる。見る点は2つある。境界を越えていないデータへの再検証や余分な nil の確認を diff が足していないか(want)。境界を越えたデータが、パースされないまま内側へ渡っていないか(want+。未検証の値で現に誤動作する経路があれば **must**)。入力そのものの安全性(注入・認可)は `security` レンズが扱う
- **領域をデータ構造に写す**: 領域の規則が条件分岐に散らばっていないか。兆候は、if / else の連なりに分岐がもう1つ増えた、既にある真偽値と同期が要る2つ目の真偽値が増えた、同じ場合分けが複数のファイルに現れた、の3つ。状態機械、表、判別共用体に写せるなら want+。ただし無理に適用しない。形が明らかで局所的で、増えそうにない分岐はそのままでよい。分岐も不正な状態も減らさず、間接だけを増やす抽象は YAGNI 違反として指摘する

## 作り替えと継ぎ足し

構造を変える diff と、既存の設計に新しい要件を入れる diff で見る。手順は `refactor-flow` スキルに在る。

- **継ぎ足し**: 新しい要件を、既存の分岐に場合分けを1つ足す形で入れていないか。「この要件が最初から前提だったら、この形にしたか」を問う。答えが否で、足した場合分けが2つ以上のファイルに現れるなら、上の「領域をデータ構造に写す」で指摘する(同じ箇所を2つの項目で拾わない)。型、文書、例、設計の理由を書いた節のどれかに古い設計が残っているなら want(読み手が古い設計に従って誤る経路が具体的なら **must**)
- **古い API の残し方**: 内部の API を作り替えたのに残った古い API と互換のための層は、上の「先に削る」で指摘する。ただし、リポジトリの外に古い API の利用者がいる場合と、古い形で保存されたデータがある場合は、互換を残すのが正しい。そのときは、残す理由と消す条件がコードのそばに書いてあるかを見る(無ければ want)。作り替える前の実装の細部だけを確かめるテストが残っていれば want
- **名前の変更の漏れと取り違え**: 古い名前が、文字列、文書、コメント、メッセージ、設定、CI の定義に残っていないかを Grep で確かめる。逆に、変えてはいけない名前(保存済みのデータのパス、ほかのツールが読む名前)が置き換わっていないかも見る。パスを要素ごとに分けて書いたコードは、文字列の保護から漏れる。保存済みのデータが古い名前を持つのに、読む側が新しい名前しか受け付けないなら **must**
- **振る舞いの固定**: 構造を変える変更に、変更の前後で同じ結果になることを示すテストか比較が無い(want+)。固定するテストが diff の外に既に在る場合は、そのテストのコマンドと結果が報告か PR の本文に示されているかを見る。示されていれば指摘しない。型検査と lint が通ることは根拠にしない
- **試作の混入**: 設計の判断のために作った試作のコード(テストの無い実験用のスクリプト、切り替えのためだけの分岐)が製品のコードに入っている(want+)
- **機械的な変更の再現**: 多くの箇所に同じ操作を当てた diff で、その操作を行ったスクリプトが、diff にも PR の本文にもコミットメッセージにも無い(want)。レビューする人が再実行して確かめられない

## 根本原因を直しているか(修正の diff)

バグ修正の diff では、症状の出た場所でなく、最初に誤った場所が直されているかを見る。

- 問い: 症状を起こした状態は正当か。正当な状態なら、症状の出た場所で扱うのが正しい。起きてはならない状態なら、そこでの確認はバグを隠すだけで、その状態を作ったコードが直っていない
- **起きてはならない状態を隠すだけの修正は must**。よくある形は、原因を直さずに足したガード(nil の確認、範囲の確認)、リトライ、無視したエラー、丸めた値、知らせずに捨てた状態である。修正方針には、その状態を作った箇所を `ファイルパス:行番号` で示す。特定できなければ want+ に下げ、`[PLAUSIBLE]` を付ける
- 同じ誤りが別の箇所にも在るのに、1箇所だけ直している(want+)。同型の箇所を Grep で探して示す
- 可観測性の観点(無視したエラーがログに出ない)は `ops` レンズが扱う

## 変更の波及の完全性

- **安全の根拠を1つ書いて確かめる**: この変更が既存の動作を壊さないと言える理由を、事実1つにして書く(例: 「この関数の呼び出し元は2箇所で、どちらも新しい引数を渡している」「旧形式の値は読み込み時に変換される」)。その事実を、低コストで到達できる段階まで確かめる。Grep で呼び出し元を全部見る(行を示した)、該当のテストをコピーの中で実行する(実行した)。grep で調べられない先(呼んでいるライブラリの実装、実行の時機、API が返す JSON、DB の列、機能フラグ)に根拠が依存しているときは、そこを明示する。確かめた結果は報告末尾の付記に書く

  ```
  影響の範囲 [design]
  - 安全の根拠: <事実を1文>
  - 確かさ: <段階>(<確かめ方。実行したならコマンドと終了コード>)
  - 残るリスク: <起きる見込みと起きたときの害。無ければ「なし」>
  - 確かめて消したもの: <疑って調べ、問題なしと分かった点>
  - 統合の前に走らせる最も安いテスト: <コマンド>
  ```

  根拠の事実が偽だと分かったら、それは指摘である(壊れる経路が具体的なら **must**)。根拠を1つも書けない変更は、段階を「主張のみ」として付記に書き、want+ で指摘する
- 構造体・クラス・API に追加されたフィールド/パラメータに、**diff の外に初期化されない構築経路が残っていないか**(コンストラクタ・リテラル構築・テストのフィクスチャ・デシリアライズ既定値)。追加箇所の diff 自体は正しくても、既存の構築箇所が旧形のまま残ると未初期化値・デフォルト欠落として実行時に出る: **must**。全構築箇所を grep で探して確認する(暗黙ゼロ初期化の無い言語では特に)。同型の「新フィールドの初期化漏れ」が短期間に繰り返された実例パターンであり、diff 内だけ見るレビューでは検出されない
