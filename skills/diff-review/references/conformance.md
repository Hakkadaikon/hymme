# レンズ: 実装適合 (conformance)

このファイルは「何を見るか」・入力の探し方・観点固有の severity 補正・確かさの段階との対応と、報告末尾に付ける付記(使った性質一覧・Pass 件数・フィルタ除外)を定義する。
severity 体系・実害ベースの貫通原則・2 パス自己検証は本体(diff-reviewer.md)に一元化されており、それをそのまま適用する。

`spec` レンズが「依頼と差分の乖離」を見るのに対し、このレンズは**明文化された不変条件・性質を実装が全経路で守っているか**を、バグ探しでなく証明の試みとして確かめる。
「バグはないか」と漠然と探すと推測の指摘が増える。性質を1つずつ主張として立て、成り立つかを論証させると、指摘は「どの経路のどこで論証が切れたか」に絞られる。

## 入力(性質一覧)

agent prompt で渡された性質一覧を使う。渡されていなければ、次の順で探して最初に見つかったものを使う:

1. 依頼文に書かれた不変条件・受け入れ条件
2. superpowers の spec(`docs/superpowers/specs/`)の要件・受け入れ条件
3. `tasks/loopeng/` の EARS・`Inv`、`tasks/fv/` の性質カタログ

どれを使ったかは報告末尾の付記に書く。どれも無ければ「性質一覧なし」と報告して終える(一般的なバグ探しに切り替えない。それは他レンズが扱う)。
diff が触れた性質だけを対象にする。diff と無関係な性質は扱わない。

**管理番号を指摘に書かない。** `tasks/` 由来の性質には `S-xxx`・`R-xx`・`P7`・`Inv` 名などの台帳 ID が付いているが、指摘本文では性質を言葉で書く(PR やコミットへ転記されて本体に入るため。規範は `${CLAUDE_PLUGIN_ROOT}/skills/_shared/stealth-artifacts.md`)。

## 手順: 性質ごとに Map → Prove → Stress-test

1. **Map**: その性質を担保するコード位置(ガード・検証・状態更新)を特定する。担保する箇所が見つからなければ、その時点で Prove は失敗。
2. **Prove**: 性質が全実行経路で成り立つことを論証する。入口ごと・分岐ごとのサブクレームに分けて明示する(例: 「経路 A はガード X を通る」「例外経路 B でも状態は更新されない」)。全サブクレームが閉じれば **Pass**。
3. **Stress-test**(論証が切れたときだけ): 切れた箇所を通る具体的な入力・呼び出し順・タイミングを組み立て、性質が破れる実例を作る。
   - 実例が作れた → **Violation**
   - 実例は作れないが論証も閉じない → **Potential**(どのサブクレームが未証明かを書く)

## 確かさの段階との対応

Pass / Violation / Potential は論証の結果で、確かさの段階(本体 diff-reviewer.md)はその結果をどこまで確かめたかである。両方を書く。対応は次のとおり。

| 結果 | 最低限の段階 | 上げ方 |
|---|---|---|
| Pass(全経路で守られるという主張) | 机上でたどった。サブクレームごとに `ファイルパス:行番号` がある | その性質を確かめるテストをコピーの中で実行して通れば「実行した」 |
| Violation | 机上でたどった。破れる実例の入力・経路・結果がある | 実例をテストかコマンドにしてコピーの中で実行し、破れを観測すれば「実行した」 |
| Potential | 行を示した。論証が切れた箇所の `ファイルパス:行番号` がある | 実例が作れれば Violation、サブクレームが閉じれば Pass に移る |

- サブクレームを書けない Pass と、実例の無い Violation は「主張のみ」である。どちらも Potential に下げる。下げずに残したものは、最後の `claim_only` に数える
- Violation は、低コストで実行できるなら「実行した」まで進める。実行できなかった理由(依存がコピーに無い、実システムが要る)は指摘に書く
- 「実システムで再現した」はこのレンズでは到達できない。並行やタイミングの実例など、動いているシステムでしか示せないものは、その旨を指摘に書いて本体に渡す

## 誤検出フィルタ(Potential / Violation を報告する前に順に通す)

1. **到達不能**: 切れた経路が本番の入口から呼ばれるか。呼ばれないなら除外する。
2. **信頼境界**: 問題の入力を外部(利用者・ネットワーク・他システム)が実際に制御できるか。上流で型・スキーマ・認証によって保証済みなら除外する。
3. **スコープ**: その性質が今回の依頼と diff の範囲に入るか。入らないなら除外する。

除外した候補は捨てずに「フィルタで除外: <どのゲート> <理由1行>」として報告末尾にまとめる。どの段で除外したかが読めると、誤検出の傾向を後から調べられる。

## severity 判定

- **must**: Violation。破れる実例(入力・経路・結果)と確かさの段階を指摘に書く
- **want+**: Potential。`[PLAUSIBLE]` を併記し、未証明のサブクレームと、閉じるために要る証拠(テスト・ガード・型)を書く
- 報告しない: Pass。報告末尾の付記に「Pass n 件 / 対象性質 m 件」の件数と、Pass の段階ごとの内訳(机上でたどった n 件、実行した n 件)を書く

## このレンズでやらないこと

- 性質一覧に無い一般的な欠陥の指摘(`design`/`security` 等が扱う)
- 論証を省いた「たぶん大丈夫」での Pass(サブクレームが書けないなら Potential)
- 実例の無い Violation(実例が作れなければ Potential に下げる)
