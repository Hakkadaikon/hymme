# diff-review: 多観点 diff レビュー

フローは 4 段階: **1. 差分収集(決定論)→ 2. レンズを決めて diff-reviewer agent を起動 → 3. 統合報告 → 4. 判定の記録**。
レビューは作業ツリーを書き換えない。修正・コミットはこのスキルの範囲外で、ユーザーの指示があってから別途行う。

## superpowers との関係

superpowers:subagent-driven-development のタスク単位レビュー(task-reviewer-prompt.md / re-review-prompt.md)と最終ブランチレビュー(requesting-code-review の code-reviewer.md)は superpowers のテンプレートで行い、本スキルはそれを置き換えない。本スキルを使う場面は 3 つ:

- **(a) PR 作成前**: pr-create が必須とし、統合の入口(PR / MR の作成、既定ブランチでの merge、PR 作成後の push)で hook が判定の記録(§4)を検査する。
- **(b) ユーザーの明示依頼**: 「レビューして」「〇〇観点で見て」。
- **(c) SDD 最終レビューの多観点補強**(任意): コントローラが code-reviewer.md の最終レビューに**加えて**本スキルを実行する。順序は code-reviewer.md → 本スキル(同じ MERGE_BASE..HEAD)。本スキルの指摘は下の対応表で severity を読み替えて最終レビューの指摘リストに加え、fix 波(1 回)と scoped re-review は SDD の手順で行う(fix 波の後に本スキルを実行して 2 回目の波を作らない)。本スキルの must が残るなら、code-reviewer.md の verdict に関わらず fix 波へ回し、merge 判断は scoped re-review の後にする。判定の3行(§4)はこの場面でも reviewer が書き、hook が記録する。後続の統合の入口がその記録を使う。executing-plans(inline)の最終レビューに足すときは、本スキルの must を Critical として1回の修正 pass に加え、executing-plans の規則どおり再レビューはしない。

diff-reviewer ワーカーはサブエージェントを起動しない。agent の分割はこのスキル(オーケストレータ)だけが決める。

### severity 対応表

| hymme(diff-reviewer) | superpowers(Critical / Important / Minor) |
|---|---|
| must | Critical |
| want+ | Important |
| want | Minor |
| nit | Minor |
| `[PLAUSIBLE]` | 読み替え後も併記。severity を上げも下げもしない |

## 1. 差分収集

`<skill-dir>` はこのファイルのあるディレクトリ。

```bash
bash <skill-dir>/scripts/collect-diff.sh manifest [<base-ref>]
```

- 出力: レビュー範囲(base / head の sha)・コミット一覧と統計・未コミット変更・未追跡ファイル・除外ファイル(lockfile 等は統計のみ)。総変更が小さければ全文 diff も同梱される
- `NO_CHANGES` が返ったら「レビュー対象の変更がない」と報告して終了する
- ユーザーがコミット範囲・ファイル等を指定した場合は base-ref 引数で範囲を合わせる
- PR 作成前のレビュー(場面 (a))は、差分をコミットしてから始める。hook は判定を「変更の ID」(ブランチのコミット済みの差分の patch-id)に結び付けて記録する。未コミットの変更はこの ID に入らないので、あとでコミットすると記録が今の変更に当たらなくなる

manifest はメインセッションで **1 回だけ**実行し、出力を次段で各 agent の prompt にそのまま入れる(agent 側に再収集させない)。メインセッションで精読・分析はしない。

## 2. レンズ決定と起動

### レンズ registry

- **既定**(無指定時に適用): `design`(設計・可読性)/ `test`(テスト設計・網羅性)
- **オプション**(指定時のみ適用): `security`(セキュリティ / OWASP Top 10)/ `docs`(ドキュメント整合)/ `performance`(計算量・N+1・データサイズ)/ `compat`(互換性・移行安全)/ `ops`(可観測性・運用)/ `concurrency`(並行性)/ `spec`(仕様一致)/ `conformance`(不変条件・性質を実装が全経路で守るかの証明試行)/ `fresh-eyes`(初見)
- キーワード対応: 「設計」「可読性」→ `design`、「テスト」→ `test`、「セキュリティ」「security」→ `security`、「ドキュメント」「docs」→ `docs`、「パフォーマンス」「性能」→ `performance`、「互換」「マイグレーション」「移行」→ `compat`、「運用」「ログ」「可観測性」→ `ops`、「並行」「排他」「race」→ `concurrency`、「仕様」「要件」「依頼どおり」→ `spec`、「適合」「不変条件」「性質を守っているか」「conformance」→ `conformance`、「初見」「fresh eyes」→ `fresh-eyes`

適用ルール:

- **追加指定**(例: 「〇〇観点も見て」): 既定レンズに**加えて**指定レンズを適用する
- **絞り込み指定**(例: 「〇〇だけ」「〇〇のみで」): 指定レンズだけを適用する
- `conformance` を適用するときは、性質一覧の場所(依頼文・spec・`tasks/loopeng/`・`tasks/fv/` のどれか)を agent prompt の「ユーザーの依頼」に含める
- registry に無い観点を指定されたら、その観点名をレンズの1つとして加え(agent を分けたときはいずれかのまとまりに入れ)、一般知識でレビューさせる

### 起動

適用レンズをまとめて diff-reviewer agent 1 体に渡す。全レンズが同じ差分を読むので、レンズごとに agent を分けると同じ差分と周辺コードを本数分読み直すことになる。分けるのは2つの場合だけで、分けた agent は **1 メッセージ内で同時に起動**する。`conformance` のように性質ごとの論証で長くなるレンズは、そのレンズだけを別の 1 体に分ける。レンズが4つを超えるときは、4つずつのまとまりに分けて1体ずつ渡す。agent の prompt には必ず以下を含める:

```
レンズ: <lens>[, <lens>...]
基準ファイル: ${CLAUDE_PLUGIN_ROOT}/skills/diff-review/references/<lens>.md(レンズごとに、レビュー開始前に Read すること)
ユーザーの依頼: <元の依頼の要約(範囲・重点の指定があれば含める)>

以下は収集済みの差分 manifest。manifest の再実行はしない。全文 diff が必要な単位のみ
${CLAUDE_PLUGIN_ROOT}/skills/diff-review/scripts/collect-diff.sh の commit / worktree / cumulative で取得する
(agent は独立コンテキストのため、ここだけは相対パスでなく絶対パス変数のまま渡す):

<manifest の出力をそのまま貼る>
```

manifest を全 agent に同一内容で渡すことで、レビュー範囲のスナップショットを固定する。

prompt に「must を 0 件と書く」「指摘を出さない」のような判定の指示を入れない。agent は依頼文より基準ファイルを優先するので、入れても従わない。

### 確かさの段階と実行での確かめ

agent は指摘と「全経路で守られる」という主張のそれぞれに、どこまで確かめたかを5段階で付ける。

| 段階 | 意味 |
|---|---|
| 主張のみ | 根拠の行も手順も示していない |
| 行を示した | 実在する `ファイルパス:行番号` を示した |
| 机上でたどった | 悪い場合が起きる(主張なら起きない)ことを、コードの上で1歩ずつたどった |
| 実行した | 実際のコードを呼ぶテストかコマンドを実行し、終了コードを得た |
| 実システムで再現した | 動いているシステムで再現した(`tasks/surface.md` の手順) |

agent は作業ツリーでテストを実行できない(Bash は hook の許可リストで制限されている)。実行で確かめるときは、コピーの中で実行するスクリプトを使う。

```bash
${CLAUDE_PLUGIN_ROOT}/skills/diff-review/scripts/run-in-copy.sh <ref> <command> [<arg>...]
```

- `<ref>` を一時の worktree に取り出し、その直下でコマンドを1つ実行して、コピーを消す。終了コードはコマンドのものが返る
- コピーに入るのはコミット済みの内容だけ。未コミットの変更、未追跡のファイル、依存の導入先(`node_modules`、`.venv` など)は入らない。依存が無くて実行できないテストは、段階を「机上でたどった」で止め、実行するコマンドを指摘に書いて本体に渡す
- `<ref>` に manifest の base を渡すと、変更前のコードで同じコマンドを実行できる。「変更前は通り、変更後は落ちる」を示せる
- 実行するのは、リポジトリに在るテストかコマンドを1つ。許可リストは、連結(`&&`、`;`、`|`)と括弧で区切った先の語も1つずつ調べる。渡すコマンドの中に連結や括弧を書くと(`sh -c 'a && b'`、`python3 -c 'f()'`)止まる。ファイルへのリダイレクトも止まる
- 出力を `| tail` などで絞る形は通るが、返る終了コードが絞った側のものになる。終了コードを得る実行には付けない

「実システムで再現した」は agent が到達できない段階である。実システムを動かす確かめは、本体が real-surface スキルの定義で行う。must の指摘は「主張のみ」のまま残さない。確かめられなければ取り下げるか、severity を下げる。

## 3. 統合報告

報告を 1 つに統合し、diff-reviewer の報告形式(must / want+ / want / nit の severity 順)で出力する:

- 冒頭に「対象: <範囲> / レンズ: <適用レンズ>」を明記する
- 同一 `ファイルパス:行番号` に複数レンズの指摘が重なったら 1 件に統合する。severity は最も重いものを採用し、レンズタグを併記する(例: `[design][security]`)
- `[PLAUSIBLE]` マークと確かさの段階は統合後も維持する。統合した指摘の段階は、重なった指摘のうち最も高いものを採る
- 段階が「実行した」の must 指摘は、付いているコマンドを本体が `run-in-copy.sh` で1回実行し直し、同じ終了コードになることを確かめてから載せる。食い違ったら、その旨を指摘に書く
- レンズ固有の付記(`design` の影響の範囲、`conformance` の使った性質一覧・Pass 件数・フィルタ除外の一覧)は、統合報告の末尾にレンズ名を付けてそのまま残す
- 場面 (c) では、hymme 形式の統合報告に加えて、対応表で読み替えた Critical / Important / Minor の一覧を最終レビューに加えるために出す(§4 の `must:` は hymme 形式の件数のまま)

### 完了条件

以下をすべて満たしたときのみレビュー完了とする。1 つでも欠けたら未完了:

- 起動した全 agent の報告を受領している(未完了の agent を残したまま統合しない)
- 全指摘が severity 順で 1 つの報告に統合されている(上記の重複統合を含む)
- 全レンズで指摘ゼロの場合は「指摘なし」と明言している。褒め言葉・社交辞令は書かない

## 4. 判定の記録

判定を書くのは reviewer で、記録するのは hook である。本体は証跡のファイルを書かない。`tasks/diff-review/evidence.md` はもう検査に使わない。

diff-reviewer は報告の最後に次の3行を書く。agent が返ったときに、hook が最後のメッセージからこの3行を読み、署名つきの記録にする。

```
must: <must 指摘の件数>
lenses: <担当したレンズをカンマ区切り>
claim_only: <確かさの段階が「主張のみ」の must 指摘と「全経路で守られる」という主張の件数>
```

- agent を2体以上に分けたときは、それぞれが自分のレンズの組で3行を書く。記録はレンズの組ごとに残る
- 記録は変更の ID に結び付く。この ID は rebase しても変わらず、コードを変えると変わる
- 統合の入口では、この変更の ID に対する記録が在り、レンズの組ごとの最新の記録で `must` と `claim_only` が 0 であることを hook が確かめる。満たさなければ止まる
- 指摘を直したら変更の ID が変わる。適用した全レンズをレビューし直す。分け方(レンズの組)は前の回と同じにする
- 指摘が誤りだと分かったときも、本体が件数を書き換える手段は無い。同じレンズの組でレビューし直し、reviewer に判定を書き直させる

この検査は `hymme exception request review --until YYYY-MM-DD --reason <理由>` で申請し、ユーザーが承認すると期限つきで外せる。
