# verifiability (形式検証の前に、判定をモデルが写せる形にする)

モデル(Z3 の性質、TLA+ のアクション、Lean の `def`)が保証するのはモデル自身で、コードではない。
保証がコードに届くかは、モデルとコードの対応の確かさで決まる。対応が確かになるのは、判定が小さな純粋関数に収まっているとき。
分岐が積み重なり、I/O・時刻・乱数・大域状態が混ざり、エラーが真偽値に畳まれていると、モデルは手で抽象化するしかなく、写し間違いがそのまま偽の保証になる。

この段は検証の手段を問わず、**コードがあるなら必ず通す**。実装前の設計検証でコードが無いときも台帳は作り、「対象コード無し」と書く。

## 強制のしくみ

この節が、ゲートが止める入口と条件の一次ソース。他のスキルはここを参照する。

- `hooks/verifiability-gate.sh`(PreToolUse)が、`loop-outer`/`loop-middle`/`loop-inner`(`SPEC=<Name>`)、`smt_oracle.py <…>/tasks/loopeng/<Name>.smt.py`、`trace_check.py <…>/tasks/loopeng/<Name>.tla`、`tasks/fv/<Name>` での `lake build` の直前に `tasks/verifiability/<Name>.md` を検査する。オプションの位置、`env`/`timeout`/`nix develop -c`/`python3` の前置き、`cd … &&` や `;` での連結があっても入口を見つける。
- 台帳は `tasks/` の手前(リポジトリ直下)の `tasks/verifiability/` に置く。台帳の中のパスもリポジトリ直下からの相対で書く(`verifiability.py` はリポジトリ直下で実行される)。
- 台帳が無い、指標が通らない、対象があるのに「## レビュー」節の合格の行が `[x]` でない、のいずれかで止まる。「## 対象」が「対象コード無し: 理由」だけの台帳は、計測の道具が無くても通す。ただし `trace_check.py`(実装後の段)は「対象コード無し(実装後): 手元に実装が無い理由」と書いたときだけ通す。
- 台帳を書くのはコントローラ。modeler/prover がゲートで止まったら、台帳を書かずに BLOCKED で返す。
- 設計時に「対象コード無し」で通した台帳は、実装が入ったら対象を書き直し、計測と reviewer の合格を取り直す(実装後の段、とくに loopeng-tracecheck と formal-verification の橋渡しの前)。
- 指標で測れないこと(対象の選び方が正しいか、例外の理由が妥当か、切り出しで振る舞いが変わっていないか)は reviewer との往復で詰める。合格が出るまで回し、合格の文言を台帳に引用してから `[x]` にする。

## 指標と閾値

| 指標 | 閾値 | なぜ検証しにくくなるか |
|------|------|------------------------|
| CCN(循環的複雑度) | 10 以下 | 分岐の数だけモデルの場合分けが増え、写し漏れと往復確認の手間が増える |
| NLOC(関数の行数) | 50 以下 | 1関数を1つの性質・1つのアクションに対応づけられなくなる |
| 引数 | 5 以下 | 入力の直積が膨らみ、全列挙も SMT の性質も書きにくくなる |
| 副作用 | 0 | I/O・時刻・乱数・モジュールの可変状態があると、純粋なモデルに写すために手で抽象化することになる |
| エラーを真偽値に畳む | 0 | 「不一致」と「取れなかった」が同じ値になり、否定をかけるとエラーが許可に化ける([`../_shared/failure-semantics.md`](../_shared/failure-semantics.md) の「エラーを真偽値に畳んで否定していないか」) |

測るのは `verifiability.py`。CCN・行数・引数は lizard が対応する言語ならどれでも測る(Python のメソッドの `self`/`cls` は数えない)。
副作用とエラーの畳み込みを拾えるのは `.py`(構文木とトークン)と `.js`/`.ts`/`.jsx`/`.tsx`/`.go`/`.rs`/`.java`(トークン)だけ。それ以外の拡張子では、この2指標は「測れない」として不合格になり、例外に理由を書いて reviewer が目で確かめる。
関数は名前の完全一致で探す。同じ名前が複数あれば、Python は `Class.method`、Java・C# など lizard がクラス名を付ける言語は `Class::method` の形で指定する。入れ子のクラスは内側のクラス名で `Inner.method` と書く。Go の型違いの同名メソッドやオーバーロードはどの書き方でも1つに決まらない(exit 2)ので、判定を別名の関数に切り出す。
誤検出は「## 例外」に `- path::function <指標>: <理由>` の形で書いて外す。理由は「モデル側でどう扱うか」まで書く(例: 「時刻は引数で受け取る形にモデルで置き換える」)。この形に合わない行は読まれない(例外が効かず不合格のまま)。理由が空なら exit 2 で止まる。

## 手順

1. **台帳を作る**: [`assets/verifiability-template.md`](assets/verifiability-template.md) を `tasks/verifiability/<Name>.md` にコピーする。`<Name>` は検証の成果物と同じ名前(`SPEC=<Name>`、`<Name>.smt.py`、`tasks/fv/<Name>`)。
2. **対象を選ぶ**: 要件の台帳(0段の抽出台帳、Lean なら性質カタログ)にある判定ごとに、それを担う関数を「## 判定の在り処」に書き、その関数を「## 対象」に挙げる。判定が散らばっていて1つの関数に担わせられないこと自体が、切り出しの対象。
3. **振る舞いを固定する**: 切り出す前に、今の振る舞いを捉えるテスト(特性テスト)を書いて緑にする。切り出しの前後で同じテストが通ることが、振る舞いを変えていない証拠になる。テストは切り出し前からある公開の入口だけを使う。公開関数の引数を変えるなら、呼び出し元を grep して全部直し、変えたことを「## 振る舞いの保全」に書く。
4. **測る**: `verifiability.py tasks/verifiability/<Name>.md`。
5. **直す**(指標ごとの定石):
   - 副作用 → 判定を `decide(入力の値) -> 結果` の純粋関数に切り出し、I/O・時刻・乱数・設定の読み込みは呼び出し側(配管)へ追い出して引数で渡す。
   - エラーを真偽値に畳む → 結果を三値(一致 / 不一致 / 判定不能)にするか、エラーを例外のまま上げる。判定不能をどちらに倒すかは呼び出し側で明示する。
   - CCN・行数 → 条件の組み合わせを判定表(データ)にして、表を引く小さな関数にする。入れ子のルール評価は、演算子ごとの小さな関数に分ける。判定表は `verifiability.py` の計測の外に出るので、表の名前を「## 判定の在り処」の担う欄に書き、モデルが表も写す対象だと明記する。
   - 引数 → 意味のまとまり(ユーザー・ルール・環境)ごとに値オブジェクトにまとめる。
6. **再計測と振る舞いの確認**: 4 と 3 のテストを回し、出力を台帳の「## 指標の記録」「## 振る舞いの保全」に貼る。
7. **レビューと修正の往復**: `hymme:verification-reviewer`(対象 `verifiability`) を dispatch し、指摘を直して再度呼ぶ。合格が出たら文言を「## レビュー」に引用して `[x]` にする。
8. 検証の段(loopeng-smt / loopeng-formalize / loopeng-tracecheck / formal-verification)へ進む。モデルは「## 対象」の関数を写す。

## やらないこと

- 閾値を満たすためだけに、判定と関係ない小さな関数を対象に挙げない(判定の在り処と対象が対応しない台帳は reviewer が落とす)。
- 判定ロジックを書き換えて「直す」ことをこの段でしない。この段は形を変えるだけで、振る舞いは特性テストで固定する。見つけた穴は検証の段で要件として扱う。
- 例外を理由なしで書かない(理由が空なら `verifiability.py` が exit 2 で止める。書式に合わない行は無視される)。
- 台帳は `tasks/verifiability/` 配下・git 管理外([`../_shared/stealth-artifacts.md`](../_shared/stealth-artifacts.md))。切り出した純粋関数と特性テストは本体に残してよいが、管理番号・手法用語を書かない。
