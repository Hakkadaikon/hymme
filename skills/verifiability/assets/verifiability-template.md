# 検証容易性台帳: <Name>

検証の手段: <SMT / TLA+ / 実ログ突き合わせ / Lean>

## 対象

モデルが1対1で写す判定の関数を1行ずつ書く(`- path/to/file::function`)。要件の台帳の判定を、ここに挙げた関数のどれかが必ず担う。
実装前の設計検証でコードが無いなら、この節を `対象コード無し: <理由>` の1行にする。

- <path/to/file>::<function>

## 例外

1行で1つの対象の1つの指標を外す。書式は `- <path>::<function> <指標>: <理由>`(この形に合わない行は読まれない)。指標名は CCN / NLOC / 引数 / 副作用 / エラーを真偽値に畳む のどれか。理由はモデル側でどう扱うかまで書く。
例: `- src/rules.py::decide 副作用: 時刻は引数で受け取る形にモデルで置き換える`

## 判定の在り処

要件の台帳の判定ごとに、担う関数を書く(対象に挙げていない場所で判定していないことの説明)。

| 判定(要件の ID) | 担う関数 | 備考 |
|------------------|----------|------|
|                  |          |      |

## 振る舞いの保全

切り出しの前と後で、同じ固定テストが通ることを書く。テストを切り出しの途中で書き換えたなら、書き換えた点と理由も書く。

- 固定テスト: <テストのファイルか名前>
- 切り出し前: <コマンド> → exit <コード>
- 切り出し後: <同じコマンド> → exit <コード>

## 指標の記録

`verifiability.py tasks/verifiability/<Name>.md` の最新の出力を貼る。

## 突き合わせ

SMT 経路で写したコードがあるなら、実関数とモデルの出力を比べるコマンドを下の行に書く(食い違う入力が0件なら exit 0)。hook はこの文字列で始まるコマンドの実行を記録する。行頭から書き、使わなければ行ごと消す。

突き合わせ: `<コマンド>`

## 変更の記録

「## 対象」のコードをあとで変えたら、変更ごとに1行書く(`- <コミットか日付> <path>::<function> <分類>: <根拠>`)。分類は 影響なし / 記述が合わなくなった / 約束を意図して変えた / 約束が破れたおそれ のどれか。「約束を意図して変えた」にはテスト・変更履歴・コミットの説明のどれかを引用する。

## レビュー

合格はここに書かない。`hymme:verification-reviewer`(対象 verifiability)が返答の最後に書く `判定: 合格 対象=verifiability 名前=<Name>` の行を hook が記録し、検証の入口はその記録を読む。記録はこの台帳と「## 対象」のファイルの内容に結び付くので、合格のあとにどちらかを変えたら reviewer を呼び直す。
