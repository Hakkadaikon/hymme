# agentloop-tracecheck (spec と実装を実ログでつなぐ)

モデル検査が保証するのは「書いた spec」で、コードではない。命令型・並行のコードは手で抽象するので、spec と実装のずれが残る。
実システムが残した状態の列を spec と突き合わせ、「この観測はモデルの正当な振る舞いか」を機械に判定させると、そのずれを実データで確定できる。
1行ずつの不変条件チェック(`used <= Cap` を各行で確かめる)では検出できない、**許されない遷移**(二重計上・取り消し・飛び越し)を検出できる。

**前提**: `tasks/loopeng/<Name>.tla` / `<Name>.cfg` が TLC を通っていること。無ければ **agentloop-modelcheck** へ戻る。実装が入った後の段なので、設計時の「対象コード無し」の台帳は対象を書き直しておく(手元に実装が無いときは「対象コード無し(実装後): 理由」。ゲートはそれ以外の「対象コード無し」を止める)。`tasks/verifiability/<Name>.md` の検証容易性の台帳が通っていること([`../verifiability/SKILL.md`](../verifiability/SKILL.md) の「強制のしくみ」)。確認の一覧と状態遷移図(`tasks/loopeng/<Name>.chart.md`)をユーザーが承認していること。図が今の spec から作られていない、破れた規則か検査されなかった規則が残る、承認が無い、のいずれかで `trace_check.py` は hook に止められる(図の作り方と申請は [`../agentloop-modelcheck/SKILL.md`](../agentloop-modelcheck/SKILL.md) の手順 4)。

## 手順

1. **観測点を決める**: spec の変数のうち、実システムで観測できるものを選ぶ。全部でなくてよい(見えない変数は spec に選ばせる)。観測は「状態」で取る。イベント名ではなく、イベントの後の変数の値。
2. **ログを JSONL にする**: 1行 = 1観測状態、キーは spec の変数名。値は整数・文字列・真偽・配列(列)・オブジェクト(レコード)・`{"$set": [...]}`(集合)。浮動小数と null、制御文字を含む文字列は使えない(exit 2)。レコードのキーは TLA+ の識別子に限る。model value は扱えない。spec が `TC_` で始まる名前を使っていると生成モジュールと衝突する。
   同じ状態が続く行(記録はしたが観測値が変わっていない)は、spec の振る舞いが同じ状態を繰り返してよいので許される。
   ログの採り方を実装に足す必要があれば、判定の外側(ミドルウェア・テスト用フック)に置き、判定ロジックに混ぜない。
   **ログは4種類採り、名前で種類を示す**: `<Name>.normal.jsonl`(正常系)、`<Name>.load.jsonl`(高負荷)、`<Name>.fault.jsonl`(障害注入)、`<Name>.broken.jsonl`(わざと壊した実装)。hook はファイル名の末尾から種類を読む。
   **ログは `hymme capture` で採る**: `hymme capture <ログ> -- <実システムを動かすコマンド>`。コマンドを実行し、その実行が書いたログのハッシュを hook が記録する。コマンドが exit 0 以外で終わるか、その実行でログが書かれなければ採れない。障害注入や壊した実装でも、ログを書き終えて exit 0 で終わるコマンドにする。手で書いたログや、採ったあとに編集したログは統合の入口で「`hymme capture` で採ったものではない」として止まる。
   **わざと壊した実装のログ**: spec が禁じる遷移を起こす変更(ガードを外す、手順を入れ替えるなど)を実装に一時的に入れ、`hymme capture` で `<Name>.broken.jsonl` を採ってから、変更を捨てる。このログが不一致にならなければ、突き合わせは実装のずれを検出できていない。観測点か spec を見直す。
3. **実行する**: `trace_check.py [--all] <Spec.tla> <run.jsonl> [--cfg <Spec.cfg>] [--timeout SEC]`。cfg の `CONSTANT` は自動で引き継ぐ(既定は spec の隣の `<Spec>.cfg`)。`CONSTRAINT`(探索を有限にするための上限)は引き継がない。TLC は既定 600 秒で打ち切る。
   - 全変数を毎行観測できる → `trace_check.py --all tasks/loopeng/<Name>.tla <run>.jsonl`。各ステップを独立に判定し、ずれを全件出す。行1が `Init` を満たすかも見る。
   - 一部の変数しか観測できない → `trace_check.py tasks/loopeng/<Name>.tla <run>.jsonl`。見えない変数は spec に選ばせ、最後の行まで届く振る舞いがあるかを判定する。報告は最初のずれ1件。
   - exit 0: ログ全体が spec の振る舞い。
   - exit 1: `不一致: N 行目は …` — その行への遷移を spec のどのアクションも説明できない。直前の行と並べて表示される。
   - exit 2: 判定できなかった。ログか spec の誤り(spec に無い変数名・JSON でない行・TLC のエラー)、TLC の時間切れ、`tlc` が PATH に無い、のどれか。
   - `trace_check.py` は Bash から直接実行する。hook が終了コード、ログの種類、ログのハッシュを記録する。スクリプトや Makefile の中から呼ぶと hook から見えず、記録が残らない。壊した実装のログの不一致(exit 1)も、hook は失敗した実行として数える。spec か cfg を変える前と後に、続けて同じ行の不一致で終わると、次の検証の入口は前提の記録を求める([`../agentloop-modelcheck/SKILL.md`](../agentloop-modelcheck/SKILL.md) の「同じ規則で2回失敗したとき」)。spec を変えたあとは、通るはずのログから実行する。
4. **ずれを判定する**: 出た行ごとに「実装の不備か、spec の書き漏れか」を決める。
   - 実装の不備: 失敗するシナリオ(agentloop-gherkin と同じ形)に固定してから実装を直す。
   - spec の書き漏れ(実装が正当に行う遷移を spec が知らない): 要件に戻って追記し、formalize → modelcheck をやり直す。spec を通すためだけに `Next` を緩めない。要件と spec が変わるので、確認の一覧と状態遷移図は作り直し、ユーザーの承認を取り直す。
   - 一部観測のモードは最初の1行しか報告しない。途中の行から切り出すと先頭行が `Init` を満たさず必ず不一致になるので、切り出しや spec の `Init` の書き換えで先へ進めない。1件ずつ直して再実行するか、全変数を観測したログを採って `--all` で全件を出す。
5. **並行の実装はアトミック版と素朴版を両方書く**: どちらの spec をログが満たすかで、実装が実際にどちらを実装しているかが確定する(read-modify-write が分離していれば素朴版だけが通る)。hook は spec のファイル名を検証の名前として扱うので、抽出の台帳、検証容易性の台帳、確認の一覧、状態遷移図は spec の名前ごとに要る。
   ログが設計の spec と粒度で合わないとき(spec はロックの取得や読み書きを別の段で写し、ログはコマンド1つにつき1行、など)は、コマンド1つを1ステップで写す spec を別の名前で作る。元の spec の検証容易性の台帳に `実ログの spec: <その名前>` と1行書くと、統合の入口は実ログの突き合わせをその名前に求める。この行を足すと台帳が変わるので、reviewer を呼び直す。

## 出口条件

- 代表的な実ログ(正常系・高負荷・障害注入の各1本以上)が exit 0。
- わざと壊した実装のログ(`<Name>.broken.jsonl`)が不一致(exit 1)になる。
- 出た `不一致` は全件、実装修正か spec 修正のどちらかで閉じている。
- 状態遷移図をユーザーが承認している(今の spec から作った図に対して)。
- ログ採取の仕組みを本体に残すなら、判定の外側に置き、管理番号・手法用語を書かない([`../_shared/stealth-artifacts.md`](../_shared/stealth-artifacts.md))。

## 統合の入口で求められること

変更がブランチの外へ出る経路(`gh pr create`、`glab mr create`、既定のブランチの上での `git merge`、PR を作ったあとの `git push`)の前に、hook が次を確かめる。検査の対象になるのは、検証容易性の台帳の「## 対象」に挙げたコードをこの変更で変えていて、spec(`.tla`)のある名前。

- `<Name>.normal.jsonl`・`.load.jsonl`・`.fault.jsonl` の突き合わせが通り、`<Name>.broken.jsonl` が不一致になった記録が、この変更に対して在る。
- 4本のログが `hymme capture` で採ったものである。
- 状態遷移図が今の spec から作られ、破れた規則と検査されなかった規則が無く、ユーザーが承認している。

記録は変更の内容(ブランチにコミットした差分)に結び付く。rebase では失効しないが、コミットした差分が変わると失効するので、突き合わせは実装の変更をコミットし終えてから通す。実ログを採れない事情があるときは `hymme exception request trace --until <YYYY-MM-DD> --reason <理由>` で期限つきの例外を申請し、ユーザーの承認を取る(期限は最長90日)。

## やらないこと

- わざと壊した変更を本体に残さない。`<Name>.broken.jsonl` を採ったら必ず捨てる。
- 1行ごとの不変条件チェックで代用しない。遷移の正しさは隣り合う2行を見ないと分からない。
- 長大なログを一度に渡して TLC を待ち続けない(既定 600 秒で打ち切る。`--timeout` で変える)。観測する変数を増やして分岐を減らすか、全変数を観測して `--all` で実行する。
- 実ログに秘密(トークン・個人情報)が入るなら、spec に不要な値はログを採る段で除く。
