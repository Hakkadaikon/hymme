# 検証が検知できる範囲を確かめて、その範囲だけを報告する

検証が通っても、ユーザーが防ぎたかったバグを検知できるとは限らない。検証の基準をエージェントが推測で置くと、基準は意図より緩くなりやすい。防ぎたいバグの種類を先に挙げ、種類ごとに検知を確かめ、確かめた範囲だけを報告する。agent-loop(TLA+ の経路と SMT の経路)と formal-verification の両方で使う。

## 防ぎたいバグの種類ごとに確かめる

1. **検証の前に、防ぎたいバグと脆弱性の種類をユーザーと挙げる。** 挙げるときの観点は次の3つ。
   - 0段の台帳の「閉じる前のチェック」(信頼境界、STRIDE、CWE、境界と失敗時の意味論、やり直しと並行)
   - 起きてはならないこと(安全性)と、いつかは起きるべきこと(活性)
   - 品質の特性(機能の正しさ、性能、信頼性、セキュリティ、互換性)
2. **確認の一覧の「## 防ぎたいバグの種類」に、種類ごとに1行書く。** 書くのは、種類と、「実証する項目」のどの行がそれを防ぐかである。防ぐ行が無い種類は「未検証」と書き、別に確かめる手段(テスト、レビュー)を添える。
3. **検証が通ったら、種類ごとに変種を作って検知を確かめる。** その種類のバグをわざと埋め込んだ版を、少なくとも1つ作る。検証に掛ける前に、埋め込んだ変更がその種類に当たることを確かめる。当たらない変種は作り直す。
   - TLA+ の経路: mutation oracle の機械的な変種に加えて、その種類のバグに当たる変更を spec に手で入れ、TLC が反例を出すことを確かめる。
   - SMT の経路: 性質ごとの壊した版(`broken`)を、その種類のバグに当たる壊し方にする。
   - Lean: 定義にその種類のバグを入れ、証明が通らなくなることを確かめる。
4. **検知できなかった種類は、検証を直す。** 直す作業には制限時間を先に決める。検証がいつ終わるかは見積もれず、結果が出ない間は「示せない」「反例がまだ見つからない」「成り立つ」を区別できないからである。時間内に直せなければ、一覧のその種類を「未検証」に書き換え、別に確かめる手段を添える。
5. **一覧を変えたら、承認を取り直す。** 「未検証」が増えたことを、ユーザーが見て判断する。

挙げなかった種類のバグは、この手順では見つからない。報告には、挙げた種類の一覧と、それ以外の種類は確かめていないことを書く。

## 報告で言える範囲

報告の主張は、1つずつ、確かめた範囲と一緒に書く。範囲を別の段落に離して書かない。

主張ごとに書くことは3つある。

- **手段**: すべての入力や順序を検査したのか、有限の入力で試したのか、コードを読んで判断しただけなのか。
- **範囲**: 値の上限、入力の長さ、試した変種の数。
- **仮定**: その主張が成り立つために置いた前提(確認の一覧の「置いた仮定」)。

次の書き方はしない。

- 有限の入力で試しただけの性質を、「どの入力でも」「常に」と書かない。「長さ3までの入力では」のように、範囲を主張の頭に書く。
- 「この種類のバグは検知できる」と書かない。「この種類の変種3個のうち3個を検知した」と、試した数を書く。
- 確かめていない前提を事実として書かない。「対象は副作用の無い関数である」「モデルは実装を正しく写している」は、確かめた方法を添えるか、仮定として書く。
- エージェントが推測で置いた基準をもとに、「バグである」「成り立つ」と言い切らない。その基準が、ユーザーの承認した一覧のどの行に当たるかを示す。当たる行が無ければ、基準をユーザーに確かめる。
- 「バグが無い」と書かない。言えるのは、挙げた種類について、確かめた範囲で検知できたことまでである。
