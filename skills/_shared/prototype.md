# 捨てる前提の試作

試作で得るのは、設計の判断か、前提の確かめであって、コードではない。試作はそのための手段で、答えが出たら捨てる。製品のコードは、選んだ案をもとに通常の工程で作り直す。

## 使う場面

- 前例がコードベースに無い設計の判断。画面の操作、構成の選び方、使い心地で決まるもの。
- 動かして観察しないと決まらない分岐。振る舞い、処理のタイミング、方式。
- 外部のライブラリやブラウザの実際の振る舞いに頼る前提の確かめ(agent-loop の spike)。

判断がすでに決まっていて、前提も確かめてあるなら、試作はしない。通常の工程へ進む。

## この場面だけ逆になる決まり

試作では、速さを優先し、コードの質を問わない。計画、テスト、カバレッジ、レビューを求めない。厳しさを向ける先は、正しい設計を安く選ぶことである。守るのは、判断を先に書くことと、観察で確かめることの2つである。頼まれていない案も出し、うまくいかない方式は捨てて別の方式を試す。

## 手順

1. **試作で決める判断か、確かめる前提を1つ書く。** 判断なら、どの配置か、どの操作か、どの方式か。前提なら、外部のライブラリがどう振る舞うか。どちらも書けないなら、試作はしない。
2. **方向が決まっていないときは、先例を集める。** 既存の実装や類例を探し、方向の候補をユーザーに示して選んでもらう。方向が決まっているなら飛ばす。
3. **リポジトリの外の、作業用のディレクトリに作る。** セッションの一時ディレクトリなど、git が追跡しない場所を使う。リポジトリの中に置くと、未コミットの変更として残るか、製品のコードに混ざる。見た目の判断なら、案を描ける最も軽い構成で作る。振る舞いやタイミングの判断なら、問いの答えが出る最小のスクリプトにする。本番で使うフレームワーク、テスト、抽象は入れない。
4. **案が複数あるときは、2〜3案を並べる。** 前提を1つ確かめるだけの試作は、1案でよい。1つの切り替え(ボタンや引数)で見比べられるようにし、案ごとに名前を付ける。
5. **判断するものを実際に動かして観察する。** 見た目の判断なら、案ごとに画面を撮り、操作する。振る舞いやタイミングの判断なら、出力を表示し、時間を記録する。ここでの確かめはアサーションではなく観察である。
6. **案、得失、勧めを示す。** 成果物は、決定と、試作を置いた場所である。出荷できるコードではない。

## 守ること

- 試作のコードを製品のコードに入れない。選んだ案は設計(superpowers:brainstorming の設計の節)へ戻し、製品のコードはテストから作り直す。
- 試作で分かったことが設計の前提を変えたら、spec と台帳を直してから進む。

## 報告

試した案、証拠(画面、観察した出力や時間)、得失、勧め、試作を置いた場所を書く。試作は捨てる前提であることを明記する。
