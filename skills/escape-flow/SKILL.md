# escape-flow — 後段の欠陥を前の段へ戻す

## このスキルの目的

結合テストや e2e、CI、本番で見つかった欠陥は、もっと前の段をすり抜けてきたものだ。その場で直して終えると、同じ種類の欠陥がまた同じ段まで届く。ここでは欠陥ごとに記録を1つ開き、拾えたはずの前の段にテストを足し、そのテストが欠陥を実際に拾うことを道具に確かめさせてから閉じる。

閉じていない欠陥の記録があるあいだ、変更は統合の入口(PR / MR の作成、既定ブランチでの `git merge`、PR 作成後の `git push`)で止まる。記録の置き場はリポジトリに1つなので、別のブランチや別の worktree の変更も止まる。この検査は例外で外せない。

**REQUIRED BACKGROUND:** 原因の調査は superpowers:systematic-debugging に従う(原因を確かめる前に直さない)。本スキルが足すのは、欠陥の記録、実物での再現、前の段へのテストの追加、閉じる手順である。

`hymme` コマンドは skill-tools に入っている(導入は [`../_shared/loopeng-toolchain.md`](../_shared/loopeng-toolchain.md))。`tasks/` は git 管理外に置く([`../_shared/stealth-artifacts.md`](../_shared/stealth-artifacts.md))。

## 1. 段を宣言する(リポジトリごとに1回)

段は前から `spec`(要件とモデル)、`unit`(単体と性質のテスト)、`integration`(結合)、`e2e`、`trace`(実ログの突き合わせ)、`ci`(CI と本番)の順である。どのコマンドとどのパスがどの段かを `tasks/stages.md` に宣言する。ひな形は [`assets/stages-template.md`](assets/stages-template.md)。

```markdown
- unit コマンド: `pytest tests/unit`
- unit パス: tests/unit/*
- e2e コマンド: `pytest tests/e2e`
- e2e パス: tests/e2e/*
```

- **コマンド**は先頭一致で照合される。実行するコマンドが宣言した文字列で始まっていること。`cd` や環境変数を前に付けた実行、スクリプトや Makefile の中からの実行は、段の実行として記録されない
- **パス**はリポジトリ直下からの glob。足したテストがどの段に在るかの判定に使う。1つのファイルが複数の段のパスに当たるときは、最も前の段として扱われる
- リポジトリのテストの置き方を調べてから書く(テストのディレクトリ、CI の workflow、`package.json` や `Makefile` のテスト用のコマンド)。推測で段を割り当てない
- 後段のテストが無いリポジトリは段のコマンドを宣言できない。`hymme exception request stages --until <日付> --reason <理由>` で申請し、作業者の承認を取る(本人が「段なし」と書くだけでは通らない)

hymme の台帳を持つリポジトリ(`tasks/` に loopeng、fv、verifiability、test-design、surface.md のどれかが在る)では、`tasks/stages.md` に段のコマンドの宣言が無いと統合の入口で止まる。パスの宣言だけでは通らない。

`tasks/stages.md` を置いたリポジトリも、台帳を持つリポジトリとして扱われる。それまで台帳が無かったリポジトリでは、置いたときから統合の入口で実物の定義 `tasks/surface.md`(real-surface スキル)と PR の本文の見出し(pr-create スキル)も確かめられる。

## 2. 欠陥の記録を開く

### 自動で開く条件

宣言した `integration` 以降の段のコマンドが失敗すると、hook が `tasks/escapes/E<日時>.md` を作り、開いた記録を残す。失敗したコマンドと出力の末尾は hook が書き込む。

次の場合は自動では開かない。

- その段のテストをこのブランチで書いている最中(その段のパスに当たるファイルを変更している)。先に書いた、まだ通らないテストの失敗は欠陥ではない
- 閉じていない記録が既に在る
- `unit` 以前の段の失敗

後段のテストを足しているブランチで、既存の後段のテストが退行したときは、自動では開かない。手で開く。

### 手で開く

作業者から報告されたバグ、本番の欠陥、CI の失敗、自動で開かなかった退行は、自分で開く。

```bash
hymme escape open --stage <段> --symptom "<症状を1文>"
```

- `--stage` は見つかった段。本番と作業者の手元で見つかったものは `ci`(最後の段)にする。CI の失敗は gh-ci-investigate スキルが調べ終えたあとに `--stage ci` で開く
- 症状は観察した事実を書く(何をしたら、何が起きたか)。原因の推測を書かない
- 1つの欠陥に1つの記録。別の欠陥をまとめない

`fix` 型のコミットがあるブランチは、そのブランチの上で開いた欠陥の記録が1件も無いと統合の入口で止まる。別のブランチで開いた記録は数えられない。修正を積むブランチに切り替えてから、直す前に開く。

欠陥の修正でない `fix`(誤字の訂正など)には記録を開かない。`hymme exception request fix_without_escape --until <日付> --reason <理由>` で申請し、作業者の承認を取る。

## 3. 実物で再現する(バグ報告からの入口)

直す前に、欠陥を自分で再現する。再現できていない欠陥の修正は当たったかどうかを確かめられない。

### spec がある領域

欠陥が spec(`tasks/loopeng/<名前>.tla`)を持つ設計に関わるとき。

1. 実システムで欠陥の起きる操作を行い、ログを採る。`hymme capture <ログ> -- <実システムを動かすコマンド>`(動かし方は real-surface スキルの `tasks/surface.md`)
2. 採ったログを spec と突き合わせる(手順は [`../loopeng-tracecheck/SKILL.md`](../loopeng-tracecheck/SKILL.md))
3. 結果で分ける
   - **不一致**: 実装が spec を破っている。実装の穴である。抜けた理由はテストの側(手法の選び違い、テストの書き漏れ、検証の弱いテスト)から選ぶ
   - **適合**: spec がその振る舞いを許している。spec の書き漏れである。抜けた理由は「要件の抜け」か「モデルで捨てた領域」になる

### spec が無い領域

再現のコマンドを書く。失敗(0 以外の終了コード)で欠陥を示し、直ったら 0 で終わるコマンドにする。記録の「再現のコマンド」の欄に書くと、`hymme escape verify` が修正前のコードで失敗し今のコードで通ることを実行して確かめる。

### 再現の規則

- **実物で再現する**。欠陥が見つかったのと同じ面(使い手の操作、API、CLI、実システムのログ)で再現する。単体テストが示すのは分岐の振る舞いで、欠陥が実物で起きないことではない
- **別の面で確かめた結果を合格にしない**。報告された経路に届かなかったのに、別の経路で動いたことを「直った」と報告しない。届かなかったら、そう書く
- **結論の出なかった確認を合格にしない**。再現したりしなかったりするなら、条件を絞るか計装して、再現する形にしてから進む
- **出す変更はすべて、実行時の証拠にたどれること**。「効くかもしれない」念のための変更は仮説で、出さない。証拠が仮説を退けたら、その仮説で入れた変更を戻す
- 直接再現できないときは、引き金を合成する、条件を絞る、ログを足して実行中に読む。状態を推測しない

## 4. 記録の欄を埋める

ひな形は [`assets/escape-template.md`](assets/escape-template.md)。欄は「- 名前: 値」の1行ずつである。

| 欄 | 書くこと |
|---|---|
| 症状 | 観察した事実を1文 |
| 見つかった段 | `spec` / `unit` / `integration` / `e2e` / `trace` / `ci` のどれか |
| 拾えたはずの段 | 見つかった段より前の段。拾えたはずの最も前の段を選ぶ |
| 抜けた理由 | 下の6分類のどれか(文字列をそのまま書く) |
| 前段に足したテスト | 足したテストのファイルのパス(リポジトリ直下から。1ファイル) |
| テストのコマンド | 足したテストだけを実行するコマンド(リポジトリ直下で実行される) |
| 水平展開 | 同じ種類の抜けをほかの箇所から探した結果。見つけた箇所か「該当なし」 |
| 再現のコマンド | 任意。欠陥を実物で再現するコマンド |
| 修正前のコミット | 任意。空なら既定ブランチとの分岐点が使われる |
| 準備のコマンド | 任意。修正前のコードを取り出した写しで、テストの前に実行するコマンド(依存の導入など) |

hook が開いた記録には「準備のコマンド」の行が無い。要るときは同じ形で1行足す。

症状、見つかった段、拾えたはずの段、抜けた理由、水平展開は、どの閉じ方でも空にできない。「前段に足したテスト」と「テストのコマンド」は、テストを足して閉じるとき(手法の選び違い、テストの書き漏れ、検証の弱いテスト)だけ必須になる。

### 抜けた理由の6分類

| 抜けた理由 | 当たる場合 | 閉じ方 |
|---|---|---|
| 要件の抜け | 要件にその振る舞いが書かれていなかった | 要件と確認の一覧を直す |
| モデルで捨てた領域 | 設計のモデルが、その領域を扱わないと決めていた | 要件と確認の一覧を直す |
| 手法の選び違い | 前の段のテストは在ったが、その種類の欠陥を拾えない手法だった | 前の段にテストを足す |
| テストの書き漏れ | 手法は合っていたが、その場合のテストが無かった | 前の段にテストを足す |
| 検証の弱いテスト | その場合を通るテストは在ったが、アサーションが欠陥を見ていなかった | 前の段にテストを足す |
| 前段では原理的に拾えない | 実環境の容量や外部の状態など、前の段では再現できない | 作業者の承認 |

「前段では原理的に拾えない」は最後に選ぶ。フェイクや小さな構成で再現できるなら、前の段で拾える。

## 5. 閉じる

どの閉じ方も最後に `hymme escape verify <id>` を実行する。通ると hook が閉じた記録を書く。記録のファイルを書き換えても、チェックを付けても、閉じたことにならない。

コマンドの中で `PATH` を変えていると、hook は結果を記録しない。`PATH` を変えずに実行する。

閉じたかどうかは `hymme escape list` で確かめる。記録ごとに「閉じた」か「開いている」が出る。テストを足さない2つの閉じ方では、`verify` は承認の前でも後でも「この閉じ方には作業者の承認が要ります」と出して 0 で終わるので、`verify` の出力からは閉じたかどうかが分からない。

### 前の段にテストを足す(手法の選び違い、テストの書き漏れ、検証の弱いテスト)

1. 拾えたはずの段に、欠陥を再現する最小のテストを足す。テストのパスは `tasks/stages.md` の宣言で、見つかった段より前の段に当たること
2. 欠陥を直す(テストを先に書いて失敗を見てから直す。superpowers:test-driven-development)
3. 記録の欄を埋め、`hymme escape verify <id>` を実行する

`verify` は次を実行して確かめる。

- 足したテストが修正前のコードで失敗する。修正前のコードは一時の worktree に取り出され、足したテストのファイルだけが重ねられる
- 足したテストが今のコードで通る
- 再現のコマンドが在れば、同じく修正前に失敗し、今は通る

コミットの順は問わない。失敗するテストを修正より前のコミットに置く必要は無い。テストと修正を1つのコミットにまとめてよい(micro-commit の粒度のまま)。

止まったときは、出た文言で次のように分ける。

- 「修正前のコードで失敗しません」: そのテストは欠陥を拾えていない。テストを直す
- 「今のコードで通りません」: 直っていないか、テストが別の理由で落ちている
- 修正前の写しには依存の導入先(`node_modules`、`.venv` など)が無い。依存が無いために落ちても「修正前に失敗」と判定されてしまう。「準備のコマンド」で依存を入れ、修正前の失敗が欠陥そのものによることを、出力を読んで自分でも確かめる

### 要件と確認の一覧を直す(要件の抜け、モデルで捨てた領域)

1. 要件へ戻る。抜けていた振る舞いを要件に足すか、捨てた領域を扱う対象に入れ直す(loop-engineering スキルの抽出と形式化の段)
2. 確認の一覧 `tasks/loopeng/<名前>.claims.md` を直し、`hymme claims request <名前>` で作業者の承認を取り直す。一覧を変えると、前の承認は失効している。確認の一覧がまだ無い領域では、ひな形([`../loopeng-formalize/assets/claims-template.md`](../loopeng-formalize/assets/claims-template.md))から新しく作る
3. 直した要件で検証をやり直す
4. `hymme escape verify <id>` を実行する。記録を開いたあとの一覧の承認が無ければ閉じない

### 作業者の承認で閉じる(前段では原理的に拾えない)

1. 記録の欄を埋める。「拾えたはずの段」には、拾おうと試した前の段を書く。拾えない理由はその段で再現できなかった事情を具体的に書く
2. `hymme escape unreachable <id> --reason "<理由>"` で申請する。hook が申請の中身を作業者に表示する
3. 作業者が `承認 <符号>` とだけ入力すると、承認が記録される。作業する本人は承認を入力できない。サブエージェントや無人の実行では、ここで止めて BLOCKED で返す
4. `hymme escape verify <id>` を実行する

申請のあとに記録を変えると、承認は当たらなくなる。変えたら申請し直す。

### 閉じたあとにコードを変えたとき

欠陥の記録は開いたブランチに結び付く。閉じたあとにレビューの指摘などでコードを変えても、閉じ直す必要は無い。足したテストは回帰として残っているので、変えたコードで通ることは通常のテストの実行で確かめる。

## 6. 水平展開

同じ種類の抜けを、ほかの箇所から探す。手順は review-feedback スキルの水平展開に従う(差分全体と周辺のコードから Grep / Read で探し、見つかれば同時に直す)。

- 探すのは2つ。同じ誤りを持つコードと、同じ抜け方をしているテスト(同じ手法の選び違い、同じ弱いアサーション)
- 結果を記録の「水平展開」の欄に書く。見つけた箇所(`ファイルパス:行番号`)か「該当なし」。空のままでは閉じられない

## 7. 台帳への追記と、繰り返しの確認

- 足したテストは test-design の台帳(`tasks/test-design/<対象名>.md`)が在れば、新しい行として加える([`../test-verify/SKILL.md`](../test-verify/SKILL.md) の回帰の固定)。テスト名やコメントに、欠陥の記録の id を書かない
- `hymme escape list` で記録ごとの開閉とファイルのパス、`hymme escape stats` で抜けた理由ごとの件数が出る。同じ理由が2回以上出ていたら、テストを1本足すだけで終えず、構造で防ぐ手段を作る(review-feedback スキルの「同じ抜けが2回出たら、構造で防ぐ」)
- 指摘や失敗から学ぶ残りの手順(埋め込み、`tasks/lessons.md` への記録)は review-feedback スキルに従う

## 完了条件

報告に次が揃っていること。

1. 欠陥の記録の id と、見つかった段、拾えたはずの段、抜けた理由
2. 再現の証拠。テストを足して閉じたときは、修正前に失敗し、修正後に通った出力(`hymme escape verify <id>` の出力をそのまま貼る)。作業者の承認で閉じたときは、再現した手順と観察した結果
3. 根本原因と修正(該当コミット)
4. 水平展開の結果

## やらないこと

- 記録を開かずに `fix` を積む。統合の入口で止まる
- 通すためにテストや再現のコマンドを弱める(skip の追加、アサーションの削除)。統合の入口が検査を弱める変更を見つけて止める
- 「前段では原理的に拾えない」を、テストを書く手間を省くために選ぶ
- 欠陥の記録の id や段の名前を、コード、テスト名、コミット、PR に書く([`../_shared/stealth-artifacts.md`](../_shared/stealth-artifacts.md))
