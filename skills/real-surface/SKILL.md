# real-surface — 実システムの定義と、実システムでの確かめ

## このスキルの目的

「テストが通った」「コンパイルが通った」は、実システムが動くことを示さない。完了の前に、使い手と同じ経路で実システムを動かし、結果を自分で見る。その動かし方を毎回思い出して組み立てると、手順が人ごとにずれ、確かめたつもりの別物を見ることになる。ここでは動かし方を `tasks/surface.md` に1回定義し、以後は同じ定義で確かめる。

**REQUIRED BACKGROUND:** superpowers:verification-before-completion(主張の前に新しい実行の証拠)。本スキルが足すのは、実システムの動かし方の定義と、その定義で動かした記録である。

hymme の台帳を持つリポジトリ(`tasks/` に loopeng、fv、verifiability、test-design、stages.md のどれかが在る)では、統合の入口(PR / MR の作成、既定ブランチでの `git merge`、PR 作成後の `git push`)で次が確かめられる。

- `tasks/surface.md` が在り、形が整っている
- 定義の「確認のコマンド」がこの変更の ID(ブランチのコミット済みの差分の patch-id)に対して通った記録が在る

`tasks/surface.md` を置いたリポジトリも、台帳を持つリポジトリとして扱われる。それまで台帳が無かったリポジトリでは、置いたときから統合の入口で段の宣言 `tasks/stages.md`(escape-flow スキル)と PR の本文の見出し(pr-create スキル)も確かめられる。

`tasks/` は git 管理外に置く([`../_shared/stealth-artifacts.md`](../_shared/stealth-artifacts.md))。`hymme` コマンドは skill-tools に入っている([`../_shared/loopeng-toolchain.md`](../_shared/loopeng-toolchain.md))。

## 定義の形

ひな形は [`assets/surface-template.md`](assets/surface-template.md)。5つの節と2つの行が要る。どれかが空だと、統合の入口で「tasks/surface.md が足りない」として止まる。

```markdown
## 起動
## 健全性の確認
## 操作
## 証跡
## 後片付け

- 確認のコマンド: `<実システムを動かして確かめるコマンドの先頭>`
- 検証と本番で違う値: <容量やタイムアウトなどの一覧。無ければ「無し: 理由」>
```

| 節・行 | 書くこと |
|---|---|
| 起動 | 起動の正確なコマンド。ポート、環境変数、種データ、認証。準備ができたことの見分け方。並べて動かせるか |
| 健全性の確認 | 「このインスタンスは動かす価値があるか」に答える、読み取りだけの確認を1つ |
| 操作 | 使い手の経路で機能を動かす方法。正確なコマンドと、観察できる結果 |
| 証跡 | 何を証跡にするかと、その置き場 |
| 後片付け | 自分が起動したものの止め方 |
| 確認のコマンド | 実システムを動かして確かめるコマンドの先頭。この文字列で始まるコマンドの実行を、hook が終了コードつきで記録する |
| 検証と本番で違う値 | 検証の環境と本番で値が違いうる定数の一覧(この1行に並べる) |

## 1. リポジトリを調べて定義を作る

推測で書かない。リポジトリを読んで、次の5点を確かめてから書く。

1. **何に触るか**: 使い手が触る面はどれか(Web の画面、HTTP の API、CLI、ライブラリの公開関数、ジョブ)。内部の設定用の関数やテスト専用の入口は面ではない
2. **どう起動するか**: リポジトリ自身の開発用のコマンドを探す(README、`package.json` の scripts、`Makefile`、`docker-compose.yml`、CI の workflow)。ポート、環境変数、種データ、認証を控える。空のデータの場所から使える状態に達する手順にする。「準備ができた」は使えることで、プロセスが応答することではない
3. **どう操作するか**: 既にあるツールを先に探す(e2e のハーネス、スモークテスト、サンプルのスクリプト)。無ければ、最小の操作を `curl` や CLI の呼び出しで書く
4. **何を証跡にするか**: 採れるものを挙げる(応答の本文、ログ、書かれたファイル、DB に入った行、送られた通知、画面のキャプチャ)。最後の画面だけでなく、操作と結果の状態を採る。見えるものと一緒に、副作用を確かめる
5. **並べて動かせるか**: 2つのインスタンスを同時に動かせるか(ポートやデータの場所を変えられるか)。できなければ、そう書く。別の worktree やサブエージェントが同時に動かして壊すのを防ぐ

そのうえで各節を書く。

- **起動**: 手で打てる正確なコマンドを書く。「サーバを起動する」とだけ書かない
- **健全性の確認**: プロセス、バージョン、ポートを使っているプロセス、認証のどれを見るかを決め、1つのコマンドにする。この確認は動かす前と、失敗や意外な挙動のあとに毎回行う。確かめていないインスタンスを動かさない
- **操作**: 使い手の経路を通る。dry-run の類は名前で判断せず、実際に何を省くかを観察してから使う
- **証跡**: 置き場を具体的に書く。後片付けのあとも、証跡がその場所に残ること
- **後片付け**: 自分が起動したものだけを止める。プロセス名で止めない(ほかの人やほかの worktree のものも止めてしまう)。証跡は消さない
- **確認のコマンド**: 起動から操作、結果の判定までを1つにまとめたコマンドにする。成功で 0、失敗で 0 以外を返すこと。既にあるスモークテストや e2e の1本が使えるなら、それを指す。無ければ小さなスクリプトをリポジトリに足す。実行するときは、ここに書いた文字列で始める。`cd` や環境変数を前に付けた実行、スクリプトや Makefile の中からの実行は記録されない

### 検証と本番で違う値

検証の環境と本番で値が違いうる定数を一覧にする。容量、タイムアウト、リトライの回数、プールの大きさ、レート制限、機能フラグ、外部サービスの接続先が該当する。

- 値ごとに、検証での値、本番での値、違いが結果に影響するかを書く
- 検証が小さな値で通っても、本番の値で同じ結果になるとは限らない。違いが影響しうる値は本番の値で確かめるか、未確認として残す
- 本物でない環境(モック、フェイク、ローカルの代わりのサービス)で確かめたときは、本物の環境が行わない準備の手順をすべて挙げる。それらは未確認のまま残る
- 違う値が無ければ `無し: <理由>` と書く(例: 「無し: 定数を本番と共有している」)。空のままでは止まる

## 2. 機能を1つ動かして、定義が使えることを示す

1回も通していない定義は下書きである。書いたら、定義のとおりに1回通す。

1. 起動する(定義のコマンドをそのまま打つ)
2. 健全性の確認を行う
3. 機能を1つ、操作の節のとおりに動かす
4. 証跡を採り、置き場に在ることを確かめる
5. 後片付けを行う。後片付けのあとも、証跡が置き場に残っていることを確かめる
6. 確認のコマンドを実行し、0 で終わることを見る

定義に書いていない手順を足さないと通らなかったら、その手順を定義に書き足してからやり直す。通すために手順を弱めない。到達できなかった入口を、別の経路で確かめたと報告しない。

実システムを動かせないリポジトリ(起動するものが無いライブラリなど)では、公開している関数を使い手と同じ形で呼ぶ最小のスクリプトを確認のコマンドにする。それも置けない事情があるときは、`hymme exception request surface --until YYYY-MM-DD --reason "<理由>"` で申請し、ユーザーの承認を取る(期限は最長90日)。

## 3. 完了前に実システムで確かめる

変更をコミットしてから、確認のコマンドを実行する。

- 記録は変更の ID に結び付く。未コミットの変更はこの ID に入らない。確かめたあとにコードを変えたら、もう一度実行する(rebase だけなら不要)
- 確認のコマンドが失敗したら、システムより先に、観察の方法を疑う(健全性の確認をやり直す。古いインスタンスを見ていないか、ポートを別のプロセスが使っていないか)
- 確かめるのはこの変更が触った機能である。確認のコマンドが変更に関係のない経路しか通らないなら、操作の節の手順で変更した機能を動かし、結果を応答に貼る
- 代わりのもの(ファイルの更新時刻、自己申告、キャッシュされた出力、「コンパイルが通る」)を証拠に数えない
- 後段のテストとして宣言した段(`tasks/stages.md`)で失敗した場合と、実システムで欠陥を見つけた場合は、escape-flow スキルで欠陥の記録を開く

## 4. 実ログを採る(`hymme capture`)

spec と突き合わせる実ログは `hymme capture` で採る。

```bash
hymme capture <ログのパス> -- <実システムを動かすコマンド>
```

- コマンドを実行し、その実行が書いたログのハッシュを hook が記録する。コマンドが 0 で終わり、指定したパスのログをその実行が書いたときだけ成功する
- `--` のあとのコマンドは定義の起動と操作の節の手順にする。ログを書くのは動かされた実システムである
- `--` のあとの引数は空白でつなぎ直してシェルに渡される。空白を含む引数を引用符でくくっても、引用符は残らない。手順が複数あるときや引用符が要るときは、スクリプト1本にまとめて渡す
- 手で書いたログ、採ったあとに編集したログは、統合の入口で「`hymme capture` で採ったものではない」として止まる。採り直す
- コマンドの中で `PATH` を変えていると、hook は記録しない
- 正常系、高負荷、障害注入、わざと壊した実装の4本を採る手順と、ログの名前は [`../loopeng-tracecheck/SKILL.md`](../loopeng-tracecheck/SKILL.md) に従う

## 5. 定義がコードの変更に追いついているかを確かめ直す

定義はコードが変わると古くなる。次のときに確かめ直す。

- 起動の方法、ポート、環境変数、認証、種データを変えたとき
- 使い手の面(画面、API、CLI のコマンド)を足したか変えたとき
- 確認のコマンドがコードを変えていないのに失敗したとき
- 定義の手順どおりに動かして、書いていない手順が要ったとき

次の順で確かめ直す。

1. **ソースと照らす**: 定義の各節を、今のコード(起動用のスクリプト、設定、ルーティング、CLI の定義)と読み比べる。ずれの疑いを挙げる
2. **実システムを通す**: ソースが問題なく見えても、必ず「2. 機能を1つ動かして」の手順を1回通す。読んだだけで「追いついている」と言わない
3. **ずれを仕分ける**
   - 定義の記述が古い: 定義を直す
   - 動くのに、定義の手順では動かせない: 操作か確認のコマンドを直す
   - 実システムが実際に正しく動いていない: 製品の欠陥である。定義を書き換えて隠さない。escape-flow スキルで欠陥の記録を開く
4. 「検証と本番で違う値」の一覧を、今の設定と照らして直す

到達できない機能は具体的な前提(認証、権限、OS、外部の状態)と試した経路を添えたときだけ「到達できないことを確かめた」と書く。

## 完了条件

- `tasks/surface.md` の5つの節と2つの行が埋まっている
- 定義のとおりに1回通し、証跡が置き場に残っている
- 確認のコマンドが今のコミット済みの変更に対して 0 で終わっている(実行したコマンドと出力を応答に貼る)
- 検証と本番で違う値のうち、未確認のものを報告に書いている

## やらないこと

- 確認のコマンドに、何も確かめないコマンド(`true`、バージョンの表示だけ)を書く。記録は付くが、実システムは確かめられていない
- 通すために操作の手順や判定を弱める
- 別の面で確かめた結果を、実システムで確かめたと報告する
- 定義の中身や `tasks/` のパスを、コード、コミット、PR に書く
