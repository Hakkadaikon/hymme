# ledger-flow — 進捗台帳と文書ライフサイクルの運用

## このスキルの目的

進捗台帳(todo・計画書・テストリスト)とスナップショット文書(STATUS・引き継ぎ・再開メモ)は、放っておくと決まった形で実態と合わなくなる:記法が場当たりに増える、同じ進捗が複数ファイルに分散して食い違う、完了主張に証跡が無い、更新がコミットより遅れる、完了済み文書が open のまま残る。実態と合わない台帳は「済んだ作業を未了と報告する」か「未検証を検証済みと報告する」かのどちらかで誤った報告をする。ここでは台帳が誤った報告をしないための運用を定める。

## 1. 記法の凡例は1箇所で定義し、増やさない

- チェックボックスの意味は台帳の冒頭(または台帳群の README)に1回だけ定義する。標準は3値: `[ ]` 未着手/未検証、`[~]` 部分完了(何が残るかを同じ行に書く)、`[x]` 完了(実装と検証の両方が実在する)。
- **早く完了にしたいという理由で凡例を増やさない**。`[対象外]` `[保留]` のような独自マーカーの新設や、「保留項目を判断記録へ移してチェックボックスの分母から外す」操作は、チェックボックスを数える機械判定(hook・自動チェック)と非互換になり、同一指摘の無限ループや誠実さの疑義を生む。スコープ外にする項目は、マーカーの新設ではなく**行ごと「対象外」節へ移し、除外理由と再登録条件を書く**。分母から外したことが読み手に見える形にする。
- `[x]` を付ける条件は「実装と検証の証跡が両方ある」。迷ったら `[~]` にする。

## 2. 進捗の真実源は1ファイルに固定する

- 計画書・テストリスト・集約 STATUS のように同じ作業を表す文書が複数あるときは、**消し込む台帳を1つ決め、他は参照だけにする**。全部を並行更新しようとすると必ずどれかが遅れ、「計画書では全部未着手・STATUS では全部完了」の食い違いが起きる。
- 計画書(plan)は write-once でよい。進捗は台帳側で消し込み、計画書には冒頭に「進捗は <台帳> を見よ」と1行書く。
- 集計値(96/103 等)を別文書へ転記しない。転記した数字は元と乖離する。載せるなら「n/m は <台帳> の集計を正とする」と出典を書く。

## 3. 完了主張には証跡ポインタを付ける

- `[x]` や「PASS」「検証済み」の記録には、**それを証明する成果物の所在**(実行ログのパス、テスト名、コミットハッシュ、CI run の URL)を同じ行か直後に書く。
- 証跡の無い PASS 記録は誤読を招く(実行結果テーブルの記号を読み違えて、実行すらしていないケースを PASS と記録した実例がある)。**記録した時点でログが実在することを確認する**。外部ランナーの結果を転記するときは、記号の意味(スキップ/非対応/失敗)を凡例で確認してから転記する。

## 4. 台帳更新はコミット・状態変化と同時に行う

- 作業をコミットしたら、その場で対応する台帳行を消し込む。「後でまとめて更新」は必ず遅れ、台帳が「済んだ作業を未了と報告する」状態になる。
- 逆に、コミットより先に `[x]` を付けない(検証前に付けると、未検証を検証済みと偽ることになる)。消し込みとコミットは同じ作業単位の中で対にする。

## 5. 文書のライフサイクルを閉じる

- **完了・不要になった文書は closed で閉じる**: 冒頭に `closed (YYYY-MM-DD), successor: <後継文書 or なし>` を1行足す。閉じない文書は、未完了のチェックボックスや「実行中」の記述を残したまま更新されなくなり、後から読む者は「これはまだ有効なのか」を調べ直すことになる。
- **スナップショット文書(STATUS・集約報告)には発行日と有効条件を書く**。「〜が全て完了」という宣言は発行後の事実で失効しうる。失効に気付いたら本文を書き直すのではなく、冒頭に失効マークと理由を足す(発行時点の記録としては残す)。
- **再開の起点は1文書に固定する**。「最新は別文書を読め」の多段リダイレクトと、セッションローカルな場所(リポジトリ外)への参照を作らない。再開メモを書き直すときは古い方を closed で閉じる。
- **台帳を別用途に転用するときは、先に退避してから上書きする**。台帳が VCS 管理外に置かれる運用(このスキル群の tasks/ 規約)では、上書きした瞬間に履歴が消える。エポックが変わるなら `<name>-<epoch>-done.md` にコピーしてから空にする。

## 6. 機械検査にできるものは機械検査にする

未チェック残・欠番・凡例違反の検査は決定論で書ける。loopeng-extract / test-design の採番台帳ゲート(hooks/hymme_hook.py の抽出の台帳の検査、hooks/test-design-extract-gate.sh)が同型の実装例で、`- [ ]` の残存と ID の欠番を PreToolUse で機械ブロックしている。恒常運用する台帳には同型の検査を用意し、目視で数える代わりにする。

## 7. SDD 台帳(superpowers)との分担

superpowers:subagent-driven-development は自前の進捗台帳 `<repo-root>/.superpowers/sdd/<plan-basename>/progress.md` を持つ(先頭行 `# SDD ledger — plan: <plan file path>`、行形式 `Task <N>: complete (commits <base7>..<head7>, review clean)` / `Task <N>: fix round <R>/5 (...)` / `Task <N>: minor (deferred): ...` / `Task <N>: parked — ... — Ruling: ...` / `Ruling: <what> — <why> — <cost if wrong>`)。所有者は superpowers。本スキルの凡例(`[ ]`/`[~]`/`[x]`)に書き換えない、チェックボックスを足さない、closed 行を足さない(plan 完了後に superpowers 自身が `rm -rf` する)。

- **SDD 実行中の真実源(§2)は SDD 台帳。** hymme 側の台帳(`tasks/loopeng/`・`tasks/test-design/`・`tasks/fv/`・`tasks/todo.md`・引き継ぎ文書)に同じ Task の進捗を転記しない。載せるなら「進捗は `.superpowers/sdd/<plan>/progress.md` を正とする」と 1 行。
- §3(証跡ポインタ)と §4(コミット前に完了を書かない)は SDD 台帳でも同じ趣旨が満たされている: `Task N: complete` 行はコミット範囲を含み、review clean か breaker で parked 済みのときだけ書かれる。superpowers が既にそう定めているので追加記法は要らない。
- hymme の台帳(T-ID 台帳・採番チェックリスト・性質カタログ・todo・STATUS)は §1〜6 に従う。例外は worktree 内の台帳で、closed 行で閉じず worktree と共に破棄する([`../_shared/stealth-artifacts.md`](../_shared/stealth-artifacts.md))。SDD の Task が hymme 台帳の消し込みを含む場合、implementer は台帳を触らず、コントローラが SDD 台帳に `Task N: complete` を書くと同時に消し込み、証跡ポインタには Task のコミット SHA を使う。
- 欠陥の記録(`tasks/escapes/E<日時>.md`)、段の宣言(`tasks/stages.md`)、実システムの定義(`tasks/surface.md`)も hymme の台帳である。欠陥の記録はチェックボックスを持たず、欄を埋めて `hymme escape verify <id>` を通すと hook が閉じた記録を書く。closed 行やチェックを手で足しても閉じたことにならない(escape-flow スキル)。
- 段の宣言と実システムの定義は、進捗を消し込む台帳ではなく、リポジトリごとに1つ置く定義である。コードやテストの配置が変わったら、その変更の中で書き直す(real-surface スキル)。hook の署名つきの記録(`<git の共通ディレクトリ>/hymme/log.jsonl`)は台帳ではない。読まず、書かず、転記もしない。
- writing-plans の plan 文書(`docs/superpowers/plans/*.md`)は §2 の「計画書は write-once」に当たる。plan 内の `- [ ]` ステップは superpowers の追跡用で、hymme の hook の対象外である(未チェックを読むのは、`hooks/hymme_hook.py` が `tasks/loopeng/*.extract.md`、`hooks/test-design-extract-gate.sh` が `tasks/test-design/*.md` だけ)。

## やらないこと

- 台帳のためだけの新フォーマット発明(既存の Markdown チェックボックスで足りる)。
- 全文書の並行更新(§2 に反する)。
- 見栄えのために informational 項目を数えて進捗率を高く見せること(分母は実装対象のみ。informational は別枠で数える)。

## 完了条件

台帳を触った作業の完了時に、次が全て成り立っている:

1. 消し込んだ行の `[x]`/`[~]` に証跡ポインタがある。
2. 対応するコミット(あれば)と台帳の状態が一致している。
3. 完了・失効した文書に closed / 失効マークが付いている。
4. 同じ進捗を表す他文書との食い違いが無い(他文書は参照に置き換わっている)。
