# TDD サイクルの運用(t-wada 流の差分)

**REQUIRED BACKGROUND:** Red→Green→Refactor のサイクルそのもの(失敗するテストを先に書く、落ちるのを見る、最小実装、緑のまま整える、テスト無しで書いたコードは捨てる)は superpowers:test-driven-development が定める。本スキルはそれを書き直さず、Kent Beck『テスト駆動開発』(和田卓人訳)の観点のうち superpowers に無い差分だけを持つ: **テストリスト先行**、**Refactor フェーズの進め方**、**仕様化テストからの合流**、サイクルを test-extract の T-ID 台帳(網羅)へつなぐ規則、そして**カバレッジ 100% をテストの側から先に満たす規則**。

Green に至る戦略(三角測量、仮実装と明白な実装)は [`tdd-green-strategy.md`](../tdd-green-strategy/SKILL.md) に分けた。
「良いテストとは何か」の規範は [`good-test-principles.md`](../good-test-principles/SKILL.md)、テストダブルの使い分けは [`test-doubles.md`](../test-doubles/SKILL.md) を参照。
**このサイクルはグリーンフィールド(新規コード)前提。** テストの無い既存コードへ後からテストを書いてから着手したいときは、
先に [`oracle-past-output.md`](../oracle-past-output/SKILL.md) の仕様化テスト(Characterization Testing)で現状の挙動を固定し、
そのテストができてから Red→Green→Refactor に合流する。

以下の手法項目は「概要」「目的/いつ使う」「TypeScript example(vitest 想定)」「落とし穴」の構成で示す。

## サイクルと T-ID 台帳のつなぎ方

superpowers のサイクルを test-catalog の台帳で進めるときの追加規則。手順自体は superpowers に従う。

1. **1 サイクル = テストリスト(T-ID 台帳)の 1 項目**。複数項目を同時に着手しない。境界・異常系も正常系と同じ重みで選ぶ(正常系ばかり先に消化すると、後半に異常系が残り、手抜きの原因になる)。
2. **Red の「落ちる理由」を台帳の項目意図と突き合わせる**。superpowers の Verify RED に加えて、落ち方がその T-ID の意図と一致していることまで確認する。
3. **Green の戦略は確信度で選ぶ**([`tdd-green-strategy.md`](../tdd-green-strategy/SKILL.md))。緑の確認自体は superpowers の Verify GREEN。
4. **項目を閉じる条件**: 一般化された実装の上で緑になり、チェックが付いた。仮実装(定数返し)が残ったままでは閉じない。作業中に気づいた抜けはその場でリストへ追記し、リストに未チェックが残るなら 1 へ戻る。
5. **リストを消化し切ったらカバレッジを測る**: 変更したコードの行(C0)と分岐(C1)が 100% であることを計測ログで確かめる。未到達が残ったときの扱いは[カバレッジ 100% をテストから先に満たす](#カバレッジ-100-をテストから先に満たす)。

網羅は、テストリストの全項目を一つずつ Red から Green へ消化し切ったときに達成される。Red→Green→Refactor の手順そのものは網羅基準を生まない。何を網羅すべきかはブラックボックス技法(同値分割、境界値)やホワイトボックス技法(分岐網羅)で定め、それらが出した項目集合を本ループが一項目ずつ消化する。停止条件は「リストが空になった」であり、手順の側ではなくリストの側にある。

## Refactor フェーズ(緑のまま設計を整える)

### 概要
緑になったテストを、意図しない変更を検出する手段として使い、振る舞いを変えずに内部構造だけを整える工程。
Red と Green が「動くものを作る」のに対し、Refactor は「動いたものをきれいにする」工程で、サイクルの最後に必ず置く。

### 目的/いつ使う
仮実装や三角測量で緑にした直後、重複やベタ書きの分岐が残っているときに使う。
Green の勢いで書いたコードには、しばしば重複と場当たりの分岐が残る。
それを次の Red に進む前に解消し、設計の負債を持ち越さない。

#### リファクタで意図しない変更を検出するテスト
緑のテストが現在の振る舞いを固定しているからこそ、内部を安心して作り替えられる。
リファクタとは「テストを緑に保ったまま」内部を変える操作であり、テストが赤になったら、振る舞いを壊したと分かる。
だから**テストを変えながらリファクタしない**。
テスト側とプロダクション側を同時に変えると、どちらが壊れたのか切り分けられず、テストが意図しない変更を検出する手段として機能しない。
テストの構造自体を直したいときは、プロダクションコードのリファクタとは別サイクルに分け、一度に一つだけ変える。

#### 緑のまま小さく刻む手順
リファクタは小さな単位に分け、各ステップで緑を確認しながら進める。

1. リファクタを一つだけ行う(重複を一箇所くくり出す、変数を一つ改名する、分岐を一段ほどく)。
2. テストを実行する。
3. 緑が維持されていることを確認する。緑なら次のリファクタへ。
4. 赤になったら、その変更を即座に戻して緑に戻す。原因を分析してから、より小さい変更に分け直す。

赤のまま次の変更を重ねない。
重ねると、どの変更が壊したのかが分からなくなり、戻す先も分からなくなる。

#### 重複除去のタイミング(Rule of Three)
重複は見つけ次第すべて消すのではなく、**三度目の出現で除去する**(Rule of Three)。
一度目は書く。二度目は重複に気づきつつ許容する。三度目で初めて共通化する。
早すぎる共通化は、まだ揃っていない構造を無理にまとめ、後で元に戻す手間が生じる。

これは仮実装・三角測量の進め方と合う。
仮実装で定数を返し、三角測量で二本目・三本目のテストを足すと、各ケースに似た処理が並ぶ。
その重複が三度目で揃ったところを Refactor で本実装にまとめると、定数返しが一般化されたロジックになる。
Green では先に一般化せず、Refactor で重複を根拠に一般化する。
(仮実装・三角測量の手順は [`tdd-green-strategy.md`](../tdd-green-strategy/SKILL.md))

### TypeScript example
三角測量で緑にした直後、各テストに重複したセットアップが並んでいる。
これを緑のまま共通化する。

```ts
import { describe, it, expect, beforeEach } from "vitest";
import { Cart } from "./cart";

// before: 各 it が同じ new Cart + addItem を繰り返している(重複が二度。三度目を待たずに整える例外として、セットアップの重複だけを共通化する)
describe("Cart 合計", () => {
  it("単一商品の合計", () => {
    const cart = new Cart();
    cart.addItem({ price: 100, qty: 2 });
    expect(cart.total()).toBe(200);
  });
  it("複数商品の合計", () => {
    const cart = new Cart();
    cart.addItem({ price: 100, qty: 2 });
    cart.addItem({ price: 50, qty: 1 });
    expect(cart.total()).toBe(250);
  });
});

// after: 重複したセットアップを beforeEach に抽出。振る舞いは不変、テストは緑のまま
describe("Cart 合計", () => {
  let cart: Cart;
  beforeEach(() => {
    cart = new Cart();
    cart.addItem({ price: 100, qty: 2 });
  });
  it("単一商品の合計", () => {
    expect(cart.total()).toBe(200);
  });
  it("複数商品の合計", () => {
    cart.addItem({ price: 50, qty: 1 });
    expect(cart.total()).toBe(250);
  });
});
```

抽出は一度に一つ、抽出のたびにテストを実行して緑を確認する。
赤になったら抽出を戻し、より小さい単位でやり直す。

### 落とし穴
- テストを変えながらプロダクションコードをリファクタし、意図しない変更を検出する手段を自分で無効にする。一度に一つだけ変える。
- 一度目の重複で共通化を急ぎ、揃っていない構造を無理にまとめる。三度目まで待つ(Rule of Three)。
- 赤のまま次のリファクタを重ね、戻す先が分からなくなる。赤になったら即座に戻す。
- 「リファクタ」と称して振る舞いを変える(挙動の修正や機能追加を混ぜる)。それは Refactor ではなく次の Red から始める別サイクル。

### 網羅とのつなぎ方
Refactor は網羅範囲を増やさない。
緑の集合を保ったまま内部を整える工程であり、新しい振る舞いを足すなら次の Red に戻る。
網羅を進めるのは Red→Green であって、Refactor はその成果を壊さず維持する。
ただし重複除去で本実装にまとめた一般化は、同値クラス全体を一例で代表できる形に近づけ、後続の網羅効率を上げる。

## テストリスト先行

### 概要
着手前に、実装すべき振る舞いを箇条書きのテストリストへ書き出す。
t-wada 流 TDD の起点であり、正常系、境界、異常系を網羅的に並べる。

### 目的/いつ使う
何を確かめるべきかを先に決め、行き当たりばったりの実装を防ぐ。
リストは一つずつ消化し、作業中に思いついた項目は随時追記する。
全項目を最初に完璧へ揃える必要はなく、分かっているものから書き出して始める。

### TypeScript example
リストはコードではなく、計画として書く。
```text
# uint パーサー parseUint のテストリスト
- [ ] "0" -> 0
- [ ] "42" -> 42
- [ ] 先頭ゼロ "007" -> 7      (正規化の境界)
- [ ] "" -> エラー            (異常系: 空)
- [ ] "-1" -> エラー          (異常系: 符号)
- [ ] "1.5" -> エラー         (異常系: 非整数)
- [ ] 巨大値の上限           (境界: オーバーフロー)
```

### 落とし穴
- 正常系だけを並べ、異常系と境界を書き忘れる。網羅の抜けがそのまま品質の抜けになる。
- リストを清書して固定文書にしようとする。リストは作業用のメモであり、消化と追記で変わり続けてよい。

### 完了チェック(もれ確認)
テストリストは「これ以上 Red を書く項目が残っていない」と言えて初めて入口として閉じる。
次を技法ごとに逆引きし、出し切ったかを確かめる([`test-extract`](../test-extract/SKILL.md) 0段の採番台帳と同じく、頭の中で済ませない)。

- **同値分割で出し切ったか**:入力空間を有効・無効の同値クラスに割り、各クラスの代表値がリストに1行ずつあるか。代表が無いクラスは未抽出(導出は [`blackbox-partition.md`](../blackbox-partition/SKILL.md))。
- **境界値で出し切ったか**:各同値クラスの端点(最小、最小−1、最大、最大+1、空、0)がリストにあるか。オフバイワンを検出する端点が抜けていないか。
- **状態遷移で出し切ったか**:状態を持つなら、各遷移(正常な遷移列)と、**起きてはいけない遷移**(禁止される列)がリストにあるか。途中まで正常で、一つの操作で禁止になる列が抜けやすい。
- **異常系を正常系と同数の重みで出したか**:正常系1件ごとに「不正入力なら? 境界なら? 並行なら?」を問い、異常系の行が系統的に書かれているか。正常系に偏っていれば未抽出。
- **リスト全項目が緑テストに対応したか(完了時)**:消化を終えた時点で、リストの各項目が実在のテストの緑に1対1で対応していること。チェック済みなのに対応する緑テストが無い項目は、閉じ忘れか仮実装の残り。逆に、どの項目にも対応しないテストは、対象外の振る舞いを固定する脆さか抽出漏れを疑う([`test-extract`](../test-extract/SKILL.md) 0段の台帳の両向き読みと同じ)。

### 網羅とのつなぎ方
テストリスト先行は、網羅の入口である。
リストの網羅性が、そのままテストの網羅性になる。
だからリストを書く段階で、正常系、境界、異常系を体系的技法で出し切る。
代表値は同値分割で、端点はオフバイワンを検出する境界値分析で、状態を持つなら状態遷移で導く。
思いつきで並べると正常系に偏り、その偏りが網羅の抜けとして残る。
出し切った項目をリスト化し、全項目にチェックが付いた時点を網羅完了とみなす。
作業中に見つけた抜けは、その場でリストへ追記して網羅対象に含める。
リストは消化と追記で変わり続け、それによって網羅の範囲が確定していく。

## カバレッジ 100% をテストから先に満たす

### 概要
TDD では、テストが要求したコードだけを書く。
そのため、サイクルを正しく進めれば、変更したコードの行(C0)と分岐(C1)はすべてどれかのテストが通っているはずで、カバレッジは 100% になる。
この節は、その 100% を後からテストを足して埋めるのではなく、テストリストの段階で先に設計し、計測で確かめる規則を定める。

### 目的/いつ使う
Red→Green→Refactor で新しいコードを書くときは常に使う。
カバレッジが 100% に届かないことは、テストに要求されていないコードを書いたことを示す。
Green で先回りして一般化した、Refactor で分岐を増やした、異常系のテストを書かずに防御コードを足した、といった TDD の逸脱を数字で見つけられる。

#### 手順
1. **テストリストで 100% に届く項目を出し切る。** 同値分割と境界値で出した項目に加え、実装に現れる見込みの分岐ごとに真と偽の両側を通す項目があるかを確かめる(C1 の基準は [`whitebox-controlflow-basic`](../whitebox-controlflow-basic/SKILL.md))。金額やセキュリティなど critical な複合条件は、各条件が単独で結果を変えることまで項目にする(MC/DC は [`whitebox-controlflow-path`](../whitebox-controlflow-path/SKILL.md))。
2. **テストを先に書いてから本番コードを書く。** 1 項目ずつ Red→Green で消化する。テストが要求していない分岐や防御コードは Green でも Refactor でも書かない。必要だと気づいたら、先にその分岐を通す失敗するテストを書き、Red から入る。
3. **リストを消化し切ったら計測する。** 変更したコードについて、行と分岐の両方のカバレッジを測る。ツールの例は vitest の `--coverage`、`pytest --cov --cov-branch`、`go test -cover`、`cargo llvm-cov --branch`。分岐を測れないツールでは、行カバレッジに加えて未到達の分岐をコードを読んで探す。
4. **未到達が残ったら、テストを後から足して埋めない。** 未到達のコードはテストに要求されていないので、まず消せないかを考える。消せないなら、そのコードを必要とする振る舞いをテストリストに追記し、次の順で Red から入り直す。コードを残したままテストを書くと最初から緑になり、Red を確かめられないため。
   1. 未到達のコードをいったん消す。
   2. 追記した振る舞いのテストを書き、落ちることを確かめる(Red)。
   3. テストが要求する最小限のコードを書き戻して緑にする(Green)。

   テストを後から足すだけでもカバレッジは上がるが、それは TDD の逸脱を隠すことになる。
5. **除外は理由を書いた場合だけ認める。** 到達できない防御コード、生成コード、プラットフォーム固有の分岐など、テストで通せないコードはツールの除外注釈(`/* v8 ignore next */`、`# pragma: no cover` 等)を付け、理由を T-ID 台帳に 1 行書く(台帳が無い単発のタスクでは、テストリストの該当行に書く)。閾値を断りなく下げない。

### TypeScript example
変更したファイルだけを対象に、行と分岐を 100% でゲートする vitest の設定。

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    coverage: {
      provider: "v8",
      include: ["src/parse-uint.ts"], // 今回変更したコードに絞る
      thresholds: { lines: 100, branches: 100, functions: 100, statements: 100 },
    },
  },
});
```

`npx vitest run --coverage` は、閾値を下回ると非ゼロで終わる。
テストリスト先行の例(`parseUint`)なら、「巨大値の上限」の項目を書き忘れたまま上限チェックの分岐を書くと、分岐カバレッジが 100% を下回るので気づける。

### 落とし穴
- カバレッジを上げるためだけにテストを後から足す。到達はしても、そのコードが本当に要るかを問う機会を失う。未到達はまず削除を考え、残すなら Red から入る。
- 行カバレッジだけを見る。`if` の偽側を一度も通していなくても行は 100% になる。分岐まで測る。
- 100% を検証の強さと取り違える。カバレッジは到達の指標で、アサーションが振る舞いを確かめているかは別に見る。critical なコードは [`mutation-testing`](../mutation-testing/SKILL.md) で確かめる。
- リポジトリ全体の数字で判断する。既存コードのカバレッジが低いと、今回の未到達を見分けられない。変更したコードに絞って測る。
- 除外注釈を理由なしに付ける。除外は台帳に理由が書かれているものだけにする。

### 網羅とのつなぎ方
テストリストの網羅は、仕様から見た振る舞いの網羅になる。
カバレッジ 100% は、その網羅が実装の構造まで届いたかを機械で確かめる検査になる。
リストを出し切ったのにカバレッジが 100% を下回るなら、リストに無い振る舞いを実装したか、リストの項目が足りないかのどちらかで、どちらもテストリストへ戻って直す。

## 実装中の予防規範

後追い修正が頻発したパターンへの対策。実装する本人(本体でも SDD の implementer でも)が守る。

- **新規プロジェクトでは、コードより先に検証ゲートを用意する**。fmt・lint・テスト・CI のゲートは最初のコミットと同時に導入する。後から導入すると、たまった違反をまとめて直すコストがかかる。
- **一括編集・一括整形は対象をファイル種別で絞ってから実行する**。フォーマッタや sed に対象外のファイル種別が混ざると、別言語として処理されて壊れる。実行直後に、対象外だったファイルも含めて構文チェック(shell なら `sh -n` 等)で破壊を検知する。
- **合否を決める側(テストランナー・検証器・CI の判定条件)のコードや設定を先に読む**。判定基準を確定してから実装すると1周で済む。判定器を読まずに実装して結果から逆推理すると、同じ機能を複数周作り直すことになる。
- **構造体や API にフィールドを追加したら、全構築・全初期化・全呼び出し箇所を grep で列挙してすべて直す**(テスト・サンプルコード含む)。可能な言語ではゼロ値初期化やデフォルト値を型側で定義し、追加漏れを構造的に防ぐ。
