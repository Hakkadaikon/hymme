## 2. 仕組みの限界(作っても塞げなかった所)

- 署名の鍵は作業者のホームにあります。本人が意図して読み出せば、記録を偽造できます。
- reviewer を起動するのは作業する本人です。依頼文で判定を誘導できます。reviewer の指示文で検査項目を優先させていますが、機械では防げません。
- スクリプトや Makefile の中から呼ばれた検証は hook から見えません。記録が無いので統合の入口で止まりますが、黙って別の検証を回すことは防げません。
- 後段のテストを足しているブランチでは、既存の後段のテストが退行しても欠陥の記録が自動では開きません。
- 修正前のコードでテストが落ちた理由は見ていません。依存が無くて落ちても「修正前に失敗」になります。
- 統合の入口は、レビューの記録が1件あれば通ります。どのレンズを当てるべきだったかは見ていません。
- Web の画面で作った PR は見えません。

### ここまでで分かったこと(途中の記録)

うまく働いた所です。

- 承認の流れは実際のセッションで働きました。一覧を変えると前の符号が失効し、申請し直しになりました。作業する本人は一度も承認を自分で入力していません。
- 検証が、承認済みの一覧の誤りを見つけました。作業者が「正しい」と認めた内容でも、検査で違うと分かれば直して承認を取り直す、という往復が1回起きています。
- 作業する本人は、ここまで hook に一度も止められていません。手順書どおりに進めれば止まらない、という状態にはなっています。

詰まった所と、直したほうがよい所です。
