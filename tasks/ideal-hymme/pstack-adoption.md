## 採否の決め方

- 「取り込む」は、台帳の行が受ける要素です。一部だけ取り込む要素は、根拠の欄に取り込まない部分を書きます。
- 「既に在る」は、hymme の該当ファイルを開いて同じ働きの記述を確かめた要素です。
- 「取り込まない」は、理由を書きます。主な理由は4つです。hymme の承認と検査の考え方と逆であること、Cursor に固有であること、検証の流れの外にあること、superpowers など別の道具が既に担っていることです。
- 台帳に行が無いのに取り込むべき内容は、表では親の要素の採否を変えず、表のあとの節に挙げます。

件数は、取り込むが33、既に在るが8、取り込まないが40で、合計81です(2026-11-23 に、強制できない要素のうち6つを「取り込む」に変えました。変えた行は根拠の欄に日付を書いています)。

## 台帳に行が無いのに取り込むべき要素

hymme の目的は、検証を機械と作業者の承認で強制することです。この目的に効くものだけを挙げます。新しい行が要るものは3つです。

### 新しい行が要るもの

1. 判定できない結果を合格にしない(フェーズ1。1-04 と 1-05 の隣)
   - 出どころは figure-it-out、swarm、bug-fix、feature、perf-issue です。
   - 理由: 1-04 は、解析できない入力と道具が無い環境で止めるか通すかを決めます。しかし、道具が走ったのに結論が出なかった場合の値がありません。証跡の形に「合格」「不合格」「判定できない」の3つの値を置き、「判定できない」と「別の面で確かめた」を入口で合格と数えない検査が要ります。`smt_oracle.py` の exit 3 は既にこの扱いです(`skills/agentloop-smt/SKILL.md:59`)。ほかの道具にも同じ扱いを広げます。
2. 検査を弱める差分に作業者の承認を求める(フェーズ4。4-12 の隣。承認は 2-07 の方法)
   - 出どころは autopilot-full の手順6、tdd の Guardrails、create-formal-verification-skill、visual-parity です。
   - 理由: 検査を通したい本人が、検査そのものを弱めることができます。台帳には、形式検証の一覧が変わったら止める行(2-08)はあります。しかし、通常のテストのアサーションの削除、skip の追加、閾値の引き上げ、検査の無効化を見つける行がありません。差分からこれらを見つけ、理由と作業者の承認が無ければ 1-14 の入口で止めます。無効にした検査は必ず元に戻す、という pstack の規則も入れます。
3. 証跡と欠陥の記録を追記のみにする(フェーズ1。1-05 と 1-11 の隣)
   - 出どころは show-me-your-work の Rules です。
   - 理由: 誤った行を消さず、上書きする新しい行を足す形にすると、書き換えを見つける検査(1-11)が単純になります。0-06 のハッシュによる検出とも合います。消された行があれば止めます。

### 既にある行の文面を広げるもの

- 1-17 に3点を足します。出どころは maintain-formal-verification-skill です。更新の前に今のまま1回走らせて結果を記録すること。更新は結果からでなくコードから書くこと。再検査が通ったら、新しいコードを壊して検査が落ちることを示し直すこと。通った検査が、落ちる力を失った記述の上で通っているおそれがあるためです。あわせて、止まった検査では同期コミットを進めない決まりも入れます。
- 4-04 に3点を足します。出どころは create-verification-skill です。健全性の確認は、動かす前と、失敗のあとに毎回行うこと。後片付けのあとも証跡が名前のある場所に残っていること。代わりの環境で確かめたときは、本物の環境が行わない準備の手順を列挙し、未確認として残すこと。3点目は 4-17 の一覧とも重なります。
- 4-12 に1点を足します。出どころは refactoring と visual-parity です。固定したテストと基準の値を、作業の途中で本人が書き換えていないことをハッシュで確かめます。基準が誤って見えるときは、書き換えずに作業者へ尋ねます。型検査と lint は固定に数えません。
- 5-10 に2点を足します。出どころは correct です。既に多く使われている型は、変更がそれを増やしたときだけ落とすこと。誤りが起こりえなくなった規則は表から外すこと。1点目は、誤って止まる回数(D-3)を抑えます。
- 5-12 に「走らせる前」の3点を足します。出どころは benchmark-checklist と principle-explain-the-number です。7つの問いの前に、出す主張を先に書くこと、計測スクリプトが何を測り何を無視するかを読むこと、機械の負荷を確かめることが要ります。結果を見てから主張を選ぶことを防ぎます。

### 対象外の節に加える候補

台帳の対象外の節は、0-11 で取り込まないと決めた要素を理由つきで加えると定めています。この文書の表で「取り込まない」とした46件のうち、対象外の節にまだ名前が無いものを、台帳を更新する担当が写してください。この文書からは台帳を編集していません。

## 取り込む要素の規則と問いの抜き書き

後の実装でそのまま使うための抜き書きです。pstack の英語の本文の要点を日本語にしました。pstack は MIT ライセンスです。文面を写す箇所の表示の方法は 0-13 で決めます。

### principle-attack-the-premise(4-16)

- 条件: 1つの前提を共有する修正が、同じ検査で2回以上落ちた。
- 前提を書き出す。落ちた修正のすべてが仮定していた1文にする。
- 前提が偽なら結果が変わる観察を探し、次の修正の前に行う。
- 失敗の大きさだけでなく、失敗の分布を見る。
- 証拠が前提と食い違ったら、前提が予測しなかった、失敗に共通する点を探す。
- 前提を書き出して確かめるまで、次の修正を始めない。

### principle-boundary-discipline(5-06)

- 検証、型の絞り込み、エラー処理は、データが境界(CLI の引数、設定ファイル、外部 API、ネットワーク)を越える場所で行う。
- 内側では型を信じる。再検証と余分な nil の確認をしない。
- 問い1: このデータは今、境界を越えているか。越えていなければ、その検証は余分。
- 問い2: これは外殻が呼ぶだけの純粋関数にできるか。できるなら切り出す。

### principle-encode-lessons-in-structure(5-10)

- 条件: 同じ指示を2回目に書いた。または同じ訂正が繰り返された。
- 規則を lint、メタデータの印、実行時の検査、スクリプトにする。
- 構造で直せるなら、構造だけで直す。指示の文は症状である。
- 判断が要って構造にできない教訓は、指示を目立たせ、失敗の例を添える。

### principle-explain-the-number(5-12)

- 走らせる前に判断を書く。その判断を変える結果と、雑音の幅を名指しする。
- 実行ごとのばらつきが効果より大きければ、止める。
- 「なぜ2倍にならないか」を問う。結果を縛る資源かコードの経路を、実行中に採ったプロファイルかカウンタから名指しする。コードを読んだ推測は要因に数えない。
- 数値が測りえた別のもの(エラー、飛ばされた処理、キャッシュ、走らなかったコード、調整していない側、雑音)を並べ、1つずつ証拠で消す。
- 実行回数、ばらつき、要因を、数値と一緒に残す。

### principle-fix-root-causes(5-06)

- 根本原因は、システムがしてはならないことをした最初の場所、または扱うべき状態を扱えなかった最初の場所。
- まず再現する。答えが「コードの誤った判断」になるまで「なぜ」を問う。
- 問い: 症状を起こした状態は正当か。正当なら、壊れた場所で扱う。あってはならない状態なら、そこでの確認はバグを隠すので、その状態を作ったものを探す。
- バグを隠すよくある形: ガード、リトライ、握りつぶしたエラー、丸めた値、捨てた状態。
- 個別でなく型を直す。同じ誤りのある場所をすべて探す。

### principle-make-operations-idempotent(5-07)

- 各手順は、前回の実行の意図からでなく、今ある状態から導く。今の状態を読み、目標と比べ、差だけを当てる。
- 実行が残すもの(ロック、一時ファイル、書きかけの記録、確保したジョブ)は、次の実行が古いと見分けられること。
- 一時パスに書いてから、名前を変えて置く。
- 問い1: これが2回走ったらどうなるか。
- 問い2: 前回の実行が、ありうるすべての地点で落ちていたらどうなるか。
- 答えが残されたものに左右されるなら、突き合わせの手順を足す。

### principle-minimize-reader-load(5-06)

- 負荷の軸は2つ。問いと答えのあいだの層の数と、頭に置く隠れた可変の状態。
- 転送するだけの層を畳む。呼び出し元が1つのラッパー、2つ目の実装が無いアダプタ、素通しのメソッド。
- 状態の範囲を縮める。変更より戻り値、フィールドよりローカル、モジュールの状態よりフィールド、大域よりモジュールの状態。
- 不変条件は、使う側ごとでなく、境界で1回だけ名付ける。
- 問い: 新しい読み手が「X はどこから来るか」「何が X を変えうるか」に30秒以内で答えられるか。

### principle-model-the-domain(5-06)

- 散らばった真偽値や段階の確認の代わりに、状態機械を使う。
- ばらばらの引数の代わりに型つきのモデル、ファイルをまたぐ分岐の代わりに表、登録簿、判別共用体を使う。
- 無理に当てない。形が明らかで局所的で伸びそうにないなら、退屈なコードを残す。
- 分岐も不正な状態も減らさず、間接だけ増やす抽象は疑う。
- 飛ばした兆候: if/else の連なりに分岐がもう1つ増える。1つ目と同期が要る2つ目の真偽値が増える。

### principle-prove-it-works(4-02、4-14)

- 実物を直接確かめる。機能を動かす。実際の値を読む。差分を調べる。
- 代わりのもの(ファイルの更新時刻、自己申告、キャッシュされた出力、「コンパイルが通る」)は数えない。
- 検査が落ちたら、システムより先に、観察の方法を疑う。
- できるなら確認をスクリプトにする。比較を再実行できる決定的なスクリプトは、1回の目視に勝る。
- 出力は作業者が見える場所に置く。

### principle-separate-before-serializing-shared-state(5-07)

- 問い: 書き手たちは1つの共有の対象が要るのか、それとも独立した事実を出しているのか。
- 既定は、書き手ごとに別のファイル、キー、ブランチ、状態のディレクトリ。読む場所でだけ合わせる。
- 2人が1つの `state.json` の別々の欄に書くのも、共有の変更である。
- 1つの書き込み先が本当の不変条件のときだけ、構造で直列にする(ロックファイル、単一の書き手、順番の段階、compare-and-swap)。
- 指示の文は並行の制御にならない。

### principle-sequence-verifiable-units(4-03)

- 各単位は、検査できる状態で終わる。今の単位が緑になるまで進まない。
- 一括の作業では、単位を「既知の良い状態、変更1つ、検査、次へ」の組にする。道具が編集するときも、単位ごとに検査する。
- 届ける順が証明になる。失敗するテストが先、修正があと。削除が先、作り直しがあと。基準が先、処置があと。
- 各コミットは単独で成り立つ。

### principle-subtract-before-you-add(5-06)

- 作る前に消す。順は、削除、構築。
- 磨く前に切る。最小にしてから品質に手を掛ける。
- 推測の端の場合でなく、観察された使われ方に合わせて設計する。
- 仕様が求める以上の、推測による検証、パーサ、ガードを置かない。
- 参照先に新しい内容が無ければ、残さず消す。

### principle-type-system-discipline(5-06)

- 目標: ありえない状態、取り違えた基本型、扱っていない場合分けを、コンパイラが退ける。
- 同じ基本型で意味の違う2つの引数には、それぞれの型を与える。作るときに1回検証する。
- 外部のデータ(JSON、RPC、CLI の引数、設定、環境変数、DB の行)は、境界のパース関数を通るまで型が無いものとして扱う。
- スキーマのファイルが形を持つなら、手書きの並行の型を作らず、そこから型を導く。

### benchmark-checklist(5-12)

- 走らせる前: 出す主張を、出す文面のまま書く。計測スクリプトを読み、何を測り、数え、無視するかを控える。`uptime` と `nproc` で負荷を確かめる。
- 問い1 なぜ2倍にならないか: 要因を名指しする。プロファイルは報告しない実行で採る。負荷をかける側が先に飽和していないかも見る。
- 問い2 調整したか: すべての側を本番と同じ形で走らせる(リリースビルド、本番の設定、接続プール、キャッシュの温度、同じ版とデータ)。片方が既定のままなら、比べたのは設定である。
- 問い3 限界を破っていないか: 算術をする。全体の10%の部分を消しても、速くなるのは最大で約11%。限界を超えた結果は、別のものを測っている。
- 問い4 エラーは出たか: 失敗と成功でない応答を数え、出力が正しいことを確かめる。スクリプトが数えていなければ、数える処理を足す。
- 問い5 再現するか: 各側を5回以上、交互(A、B、A、B)に走らせ、中央値と範囲を報告する。ばらつきより小さい差は、差なしとする。
- 問い6 意味があるか: 小さな結果の隣で、使い手が待つ端から端の経路を測り、全体に占める割合で報告する。
- 問い7 そもそも起きたか: 計測の区間の中で作業が走ったことを確かめる(要求が届いた、行が書かれた、結果が使われた)。
- 報告: 判定(速い、遅い、差なし、結論なし)を先に書く。数値には単位、回数、範囲、要因を付ける。要因を名指しできない、片方が未調整、問い4と7を確かめられない、のどれかなら「結論なし」とする。

### blast-radius(5-01、5-05)

- 確かさの5段階。1 主張しただけ(それだけでは無価値)。2 行を示した(実在の `file:line`)。3 悪い場合が起きないことを机上で1歩ずつたどった。4 実行した(実物のコードを呼び、誤りなら大きく落ちるスクリプトかテスト)。5 動いているアプリで再現した。
- 安全の根拠となる事実ごとに、安く行ける段まで進め、どこで止まったかを書く。
- 手順: 変更を読む。安全である理由の1つの事実を見つける。grep が止まる先を見る(呼んでいるライブラリのソースと固定された版、実行の時機、API が返す JSON、DB の列、通信の形式、機能フラグ、3段先のコード)。
- リスクごとに、起きる見込みと起きたときの害を正直に書く。確かめて消したものは別に並べる。
- 実在の `file:line` を引く。何も見つからない検索も答えである。呼び出し元や API を作り上げない。
- 返すもの: 何をするか。安全である理由の1つの事実と、達した段と、証明(証明できなければ「未証明」と書く)。リスク。確かめて消したもの。マージの前に走らせる最も安いテスト。

### correct(5-09、5-10、1-12)

- 誤りの型は、2回起きたら1つと数える。最近のコミット、revert、レビューのコメント、agent 向けの指示、回避策を説明するコメントから集める。
- 前提: 貢献者は、開いたファイルしか見ず、最も近い例を写し、コンパイルが通る最短の道を取る agent である。
- 直す段の順。1 設計で無くす(状態の持ち主を1つに、やり方を1つに、手で同期する一覧を1つの源に、写されそうな古いやり方を消す)。2 型で書けなくする。それでも通るなら、エラー文が使うべきファイル、型、関数を名指しする lint か CI の検査を足す。3 振る舞いをテストする。4 文書と agent の規則は最後に、判断が要るものだけに書く。
- 既に多い型は、変更がそれを増やしたときだけ落とす。
- 新しい検査は、実際に起きた過去の誤りで落ちることを示す。同じコマンドを手元と CI で走らせる。
- 例外は、該当する行に、理由、期限、人の承認とともに置く。
- 規則と、それを強制するものの対応表を保つ。規則が既に表にあり強制が無いのに破られたら、それは繰り返しなので、同じ変更の中で最も高い段で直す。誤りが起こりえなくなった規則は外す。
- 報告: 型ごとに、証拠、選んだ段、より高い段が使えなかった理由。

### create-formal-verification-skill(1-15、2-01、2-02)

- 対象の選び方: コードがする約束のうち、破れると使い手に害があり、テストが破れる場合に届きにくいもの。検証しやすいものでなく、最も強い対象を選ぶ。
- コードに忠実: モデルや証明の各部分が、レビューする人が開けるコードを指す。検証が不可分の1歩として扱うものは、コードでも不可分の1歩である。
- 落ちる力: 落ちるのを見たことのない検査は何も証明しない。性質ごとに、守っているコードの壊した版(検査の削除、手順の入れ替え)で落ちることを示す。
- 見つけたものは見つけたものとして残す: 今のコードが性質を破るなら、反例をコードの言葉で報告する。通るまで性質やモデルを弱めない。
- 範囲に正直: 何を検証したか、どの上限と仮定のもとか、何を除いたかを書く。合格が覆うのはモデルか上限であり、システム全体ではない。
- 道具が無くても読める: 性質と害を、平易な1文ずつで書く。反例は、コードの言葉の短い手順の列として語る。
- コードと歩調を合わせる: 検査ごとに、覆うファイルと関数、検証がそれらを記述していると最後に確かめたコミットを記録する。同期コミットは、新しいコミットで記述が合うと確かめたあとにだけ進める。
- 渡す前の証明: 実コードで性質を破る仮の変更を入れ、生成したスキルの手順どおりに1回たどる。破れを捕まえること。仮の変更を捨て、検査が元の状態に戻ったことを確かめる。1回も走らせていないスキルは下書きである。

### create-verification-skill(4-04、4-05)

- 調べる5点。面(使い手が触るもの)。起動(リポジトリ自身の開発用コマンド、ポート、環境変数、種データ、認証)。操作(既存のハーネスを先に探す)。観察(採れる証跡)。隔離(2つを並べて動かせるか。できなければそう書く)。
- Launch: 起動の正確なコマンドと、準備ができたことの見分け方。空のデータの場所から使える状態に達すること。「準備ができた」は使えることであり、プロセスが応答することではない。
- Doctor: 「このインスタンスは動かす価値があるか」に答える、読み取りだけの確認を1つ(プロセス、版、ポートの持ち主、認証)。
- Evidence の基準: 内部の設定関数やテスト専用の口でなく、使い手の経路を通る。最後の画面だけでなく、操作と結果の状態を採る。見えるものと一緒に、副作用(書かれたファイル、入った行、送られた通知)を確かめる。dry-run は、名前を信じず、実際に何を省くかを観察する。
- Cleanup: 自分が起動したものだけを止める。プロセス名で止めない。証跡は消さず、スキルが名指しした場所に残す。
- 機能の一覧: 機能ごとに1ファイル。節は「下位の機能」「使い手から見た行き方」「ハーネスでの動かし方(前提、操作、正確なコマンド、観察できる結果)」「落とし穴」の4つ。届かなかった入口を、別の経路で確かめたと報告しない。通すために手順を弱めない。
- 渡す前の証明: 起動、健全性の確認、機能1つの操作、証跡の採取、後片付けを1回通す。後片付けのあとも証跡が名指しの場所にあることを確かめる。
- 代わりの環境で証明したときは、本物の環境が行わない準備の手順をすべて列挙する。それらは未確認のまま残る。

### interrogate(5-02、5-03)

- 範囲は利用者が名指ししたもの。無ければ、基準のブランチとの合流点から作業ツリーまでの差分。
- 敵対役への指示: 変更を壊せ。指摘ごとに、実物のコードに対する実行(失敗するテスト、再現スクリプト、誤った振る舞いを示すコマンドの出力)で証明せよ。
- 指摘の形: 題、正確なコマンド、出た出力、意図が求める出力。
- 実行していないものは除く。書き方、命名、構造、将来の変更があって初めて問題になるリスクが当たる。
- 「指摘なし」は正当な結果である。
- 検証: 指摘ごとにコマンドを再実行する。出力が失敗を示し、その失敗が意図を破るものだけを残す。根本原因が同じ指摘はまとめる。
- 出力: 意図。指摘(コマンド、出力、意図をどう破るか)。落とした指摘の件数と理由。

### maintain-formal-verification-skill(1-15、1-17、1-18)

- 検査ごとの結果は4つ。同期している。更新した。バグ(検証は今のコードを記述しており、コードが性質を破る)。止まった(合わせ直せないか走らせられない。理由を正確に書く)。
- 編集してよいのは検証だけ(モデル、ハーネス、性質、スキル自身)。製品のコードは触らない。今のコードで性質が落ちても、通すために性質やモデルを弱めない。
- 手順2: 何も変える前に、今のまま1回走らせて結果を記録する。ここでの合格は、コードが正しいことでなく、古い記述がまだ成り立つことを示すだけ。
- 手順3: 同期コミットから今までの、覆う対象の差分とコミットの説明をすべて読む。名前の変更、分割、移動も追う。守っている状態に触る新しいコードも探す。
- 変更の4分類。影響なし(コミットの説明でなく、モデルかハーネスと照らして確かめる)。検証がコードを記述しなくなった。約束を意図して変えた(doc コメント、テスト、変更履歴、コミットの説明のどれかの証拠を引用する)。約束が破れたおそれ(約束が変わったという証拠が無い)。
- 手順4: 結果からでなくコードから更新する。再実行の前に更新を書く。性質を変えるのは、意図して変わった約束のときだけ。古い文面、新しい文面、証拠を書く。上限を下げたら報告に書く。
- 手順5 合格のとき: 新しいコードを、性質が守る形で壊し、検査が捕まえることを確かめてから、壊した変更を捨てる。
- 手順5 不合格のとき: 反例を実コードで1歩ずつ再生する。起こりえない歩があれば検証の誤り。すべて起こりうるならバグ。入れたコミット、コードの言葉の手順の列、害の1文を書く。
- 止まった検査では同期コミットを進めない。検証の更新は、製品の修正と別の変更にする。

### maintain-verification-skill(4-06)

- 結果は3つ。問題なし(全機能をソースと実機で覆い、直すものが無い)。変更した(証明した訂正を1つの PR に)。止まった。
- 編集してよいのは検証スキルのディレクトリだけ。一覧が述べる振る舞いをアプリがしなくなっていたら、文書のずれ(一覧を直す)か製品の退行(報告する。文書で覆い隠さない)。
- ソースの波: 機能のファイルごとに読み取り専用の担当を並列に出す。返す形は、機能の要約、ソースの入口、ずれの疑い、実機での確かめ方1つ。
- 実機の通し: ソースが問題なく見えても必ず行う。全機能を1回以上動かす。
- 守る3つ。意外な挙動のあとに健全性を確かめていないインスタンスを動かさない。それまでに採った証跡が、どの後片付けのあとも名指しの場所に残る。操作が起動したものを、役目のあとに残さない。
- 届かない機能は、具体的な前提(認証、権限、OS、外部の状態)と試した経路を添えたときだけ「到達不能を確認」とする。
- 仕分け: 使い手から見た記述の誤りは文書のずれ。動くのにハーネスが動かせないものはハーネスの穴。アプリが実際に壊れているものは製品の穴で、利用者に記録して渡し、この PR に入れない。

### statechart(0-07、2-12、2-13、2-14)

- 読み手が同意した規則を、1つずつ INVARIANT として書く。モデルに変数が無ければ足す。成り立たせるために規則を弱めない。
- `Next` はアクションの選言として書く。そうしないと、道具がすべての歩を `Next` と呼ぶ。
- 状態の名前は、読み手が見えるものか気にするものにする。変数名を入れない。矢印の名前は、使い手に起きることとして書く。コードやアクションの名前を出さない。
- 図は矢印を約20本以下にする。まとめるときは、バグの経路の状態と印を残す。違う規則を破る2つの状態をまとめない。歩を隠したら、渡すときに何を隠したかを言う。
- 報告には「検査しなかった規則」の一覧がある。検査しなかった規則は、成り立つとも破れるとも言えない。
- 図の上限は500状態。超えると、破れる規則への経路だけを描く。
- 渡すとき: バグごとに1行(規則、読み手の言葉での規則の文、報告の番号の経路)。モデルが省いたものを言う。再生成のコマンドを渡す。
- モデルがコードを記述するなら、バグの経路を実コードでテストか再現として再生する。バグが起きなければ、そうでないと示すまでモデルが誤りと考える。

### playbook: autopilot-full(1-12、1-13)

- 判定が覆うのは1つのパッチ。緑の CI が覆うのは1つの head。新しい head には、その head の緑の CI が要る。
- PR を止めるのは、示せる問題があるときだけ。head での失敗する実行か、PR が誤りにした文書の行。基準のブランチが既に持つ問題は、PR が写すか新たに届かない限り止めない。
- 緑の CI だけではマージを認めない。
- 検査を緩めるもの(予算の引き上げ、許可リストへの追加)は、検証役の証明と、新しい連署が要る。持ち主は緑にしたい当人だからである。
- 検査の無効化と、落ちても通す設定は、必ず取り除く(原文は "always comes out")。その検査が、あらゆる場合の見張りをやめてしまうからである。
- 仕組みが強制する承認は、与えも迂回もしない。

### playbook: bug-fix(4-01、4-02、4-03)

- 出すすべての行が、実行時の証拠にたどれること。「効くかもしれない」念のための変更は仮説であり、出さない。証拠が仮説を退けたら、その仮説で入れた変更を戻す。
- 手順1: 合う面で自分で再現する。直接再現しなければ、引き金を合成する、条件を絞る、計装する。
- 手順2: 原因を二分する。仮説を並べ、残る問題の空間を最も大きく切る分け方を取り、実行時の証拠で消す。状態が不明なら、ログを足して実行中に読む。推測しない。
- 手順4: 同じ面で確かめる。元の再現が通ること。「結論なし」と「別の面」は合格でない。印を付ける。単体テストが示すのは分岐の振る舞いであり、バグが無いことではない。
- 手順5: git の履歴で、失敗する再現が修正より前に来るようにコミットを並べる。テストが高価、結合が重い、不明確なときは省いてよい。
- 報告: 何が壊れていたか、根本原因、修正、確かめ方。失敗してから通る再現の出力を、そのまま貼る。

### playbook: opening-a-pr(5-11)

- 題は `type(scope): subject`。変更を担う実在の記号があれば名指しする。
- 本文は1分で読める40行未満。見出しはこの順で、空のものは落とす。Why、What changed、Scope、Tradeoffs(レビューする人が尋ねそうな退けた案だけ)、Blast Radius、Verification。
- 証跡のログ、実行の履歴、長い表は、ファイルか PR のコメントに置き、本文からリンクする(worker.md)。
- 下書きにしない方針は取り込まない。

### playbook: refactoring(4-12)

- 構造は変わる。振る舞いは変わらない。掃除の途中で足りない機能や本当のバグが見つかったら、切り離す。
- 手順1: 先に振る舞いの約束を固定する。構造を動かす前に、今の振る舞いを捉える特性テスト、スナップショット、等価性のハーネスを書く。覆いが無い領域では、触る前に固定を書く。型検査と lint は固定でない。
- 手順5: 振る舞いを保つ小さな歩で動かし、歩ごとに固定を緑に保つ。名前の変更は、実際のファイルで抜き取って確かめる。文字列、文章、逆向きの参照の中の使用が黙って漏れる。
- 手順6: 「コンパイルが通る」でなく、実物で不変を証明する。大きな作り直しでは等価性の確認をする(古い出力と新しい出力を比べるスクリプト、記録した基準の再生、合う面での試運転)。
- 手順7: 読み手の負荷がどこかで下がっていなければ、戻す。
- 報告: 変わった構造、固定に使ったもの、等価性の証明、戻したもの。

### playbook: shipping(1-13)

- 数えるのは、コードを書いていない agent の判定だけ。書いた者は、作るつもりだったものを確かめてしまう。緑の CI と、承認する bot のレビューは判定でない。
- 判定は `PASS`、`PASS+NOTES`、`FAIL` の3つ。
- 判定が覆うのはパッチ。連なる rebase は、どの検査も落とさずに、上の PR をすべて新しい SHA へ動かす。古い判定を信じる前に、判定時の SHA と今の head の `git patch-id` を比べる。
- パッチの違いがテスト、文書、lint の設定だけなら、その検査が走らせたものが両方の SHA で同じに組み上がる限り、結果は有効。変更そのものには、新しい検査とレビューが要る。
- 雑音とは、判定時の SHA を2回組んでも出る差、または埋め込まれたコミットの SHA。雑音は種類ごとに、ファイルを添えて報告する。
- 組み上がった出力の無い検査(開発サーバなど)は、同じだと示せないので、再実行する。
- マージの命令のあとは、PR を読み直して結果を確かめる。命令が成功を返しても、待ち行列に入っただけのことがある。
