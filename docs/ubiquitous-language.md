# ユビキタス言語

hymme の文書、スキル、hook のメッセージで使う語を1つに決める。同じものを別の語で呼ばない。

## 対象

| 対象 | 例 |
| --- | --- |
| 文書 | `README.md`、`docs/`、`tasks/` の新しい文書 |
| スキルと agent の文面 | `skills/**/*.md`、`agents/*.md` |
| 端末に出すメッセージ | hook とスクリプトの `MESSAGES`、`msg()` |
| コードの中の日本語のコメント | `*.py`、`*.sh` |

英語で書くもの(コードの識別子、英語のコメント、コミットメッセージ)は対象外。

## 基本の方針

- 開発の現場で定着したカタカナ語は、和語に開かない。「ツール」を「道具」と書かない。
- hymme が独自に決めた語は、下の「hymme の用語」の定義どおりに使う。
- 表に無い語で迷ったら、ふだんの技術文書で見かける言い方を選ぶ。決めたら、この文書に足す。

## 言い換える語

左の語を使う。右の語は使わない。

| 使う語 | 使わない語 | 意味と注意 |
| --- | --- | --- |
| ツール | 道具 | コマンドやプログラム。Claude Code の tool も「ツール」 |
| メッセージ | 文言 | hook やスクリプトが端末に出す文字列 |
| ユーザー | 作業者 | Claude Code を使う人。承認を入力する人 |
| エージェント | 作業する本人 | 作業している AI。subagent と区別するときは「メインセッション」と書く |
| 承認コード | 符号 | 申請ごとに出る8桁の16進の文字列。入力は `承認 <承認コード>` |
| 実システム | 実物 | 実際に動かしたシステム。「実システムで確かめる」「実システムの定義」 |
| 状態遷移図 | 状態の図 | `hymme chart draw` が描く図 |
| コピー | 写し | 一時の worktree に取り出したリポジトリ。手で写した一覧も「コピー」 |
| インストール(する) | 入れ方、(インストールの意味の)入れる | プラグインやツールの導入。「PATH に入れる」「表に入れる」はそのまま |
| ラップする | 包む | 別のコマンドで包んで呼ぶこと |
| ルーター | 案内役、入口ルーター、入口のスキル | 局面を見て工程のスキルへ振り分けるスキル |
| ワーカー | 作業役 | 親から仕事を渡されて動く agent |
| エントリポイント | 起動ファイル | hook が最初に呼ぶファイル |
| バージョン | 版 | ソフトウェアの version。「先行版」「動作確認版」はそのまま |

言い換えると助詞が合わなくなる文は、文ごと自然に直す。意味、条件、言い切りの強さは変えない。

次の使い方は別の意味なので、言い換えない。

| 語 | 言い換えない使い方 |
| --- | --- |
| 写す(動詞) | 実装の判定をモデルへ書き移すこと。「検証が写したコード」「モデルに写す」 |
| 写し間違い、写し漏れ | 上の「写す」で起きる誤り |
| 文言 | 仕様、依頼、台帳に書いてある言い回し。「仕様の文言」「台帳の文言」 |
| ユーザー | 作る製品を使う人。「エンドユーザー」「ユーザーの操作」 |
| 版 | 実装の種類。「壊した版」「素朴版」「軽量版」 |
| 実物 | テストダブルに対する本物の依存 |
| 符号 | 数値の正負 |
| 入れる | 含める、書き込む。「PATH に入れる」「指示を入れない」 |

## hymme の用語

言い換えずに、この意味で使う。

| 用語 | 意味 |
| --- | --- |
| 台帳 | 進み具合や検査の対象を書いた、チェックボックスつきの文書。`tasks/` に置く |
| 記録 | hook が署名して書いた1件のデータ。台帳と区別する |
| 検証の入口 | 検証を始めるコマンド。`loop-*`、`smt_oracle.py`、`trace_check.py` など |
| 統合の入口 | 変更がブランチの外へ出るコマンド。PR の作成、既定のブランチへの merge、push |
| 検査 | 条件を1つ確かめること。入口で止める仕組みの全体は「ゲート」と呼ぶ |
| ゲート | 入口で、検査がそろうまで実行を止める仕組み。「統合ゲート」「検証容易性ゲート」 |
| 段 | テストや確かめの段階。前から spec、unit、integration、e2e、trace、ci |
| 前段、後段 | ある段より前の段、後ろの段。「後段」だけで言うときは integration 以降 |
| 欠陥の記録 | 後段で見つかった欠陥を書くファイル。`tasks/escapes/` に置く |
| 抜けた理由 | 欠陥が前段で拾えなかった理由。6種類から選ぶ |
| 確認の一覧 | 何を実証するかをユーザーに見せる一覧。`<名前>.claims.md` |
| 実ログ | 実システムを動かして採った状態のログ |
| 突き合わせ | 2つのものを比べて、食い違いを探すこと。「実ログと spec の突き合わせ」 |
| 証跡 | 確かめた結果を残したファイルやログ |
| 例外 | ユーザーが承認して、期限つきで検査を外すこと |
| 本体 | subagent を呼ぶ側のセッション。「メインセッション」と同じ。「hook の本体」のような普通の意味でも使ってよい |

## 英語のまま書く語

訳さない。カタカナにもしない。

- ツールとスキルの名前: hook、subagent、agent、worktree、spec、diff-review、verifiability など。
- git の語: commit、merge、push、rebase、PR。「コミット」「ブランチ」「レビュー」は定着しているので、カタカナでよい。
- 判定の値と目印: `HOLDS`、`VIOLATED`、`must:`、`lenses:`、`claim_only:`。

## プログラムが読む文字列

次の文字列は、hook やスクリプトが台帳やメッセージから読む。この文書の言い換えを当てはめない。変えるときは、読む側のコードとテストを同じコミットで変える。

| 文字列 | 読む場所 |
| --- | --- |
| `承認 <8桁>` の「承認」 | ユーザーの入力 |
| `判定: 合格 対象=<系統> 名前=<名前>` | verification-reviewer の最後のメッセージ |
| 欠陥の記録の項目名(「症状」「見つかった段」「拾えたはずの段」「抜けた理由」「前段に足したテスト」「テストのコマンド」「水平展開」) | `tasks/escapes/*.md` |
| 抜けた理由の6種類(「要件の抜け」「前段では原理的に拾えない」など) | 同上 |
| 実システムの定義の見出し(「起動」「健全性の確認」「操作」「証跡」「後片付け」)と項目名(「確認のコマンド」「検証と本番で違う値」) | `tasks/surface.md` |
| 確認の一覧の見出しと列(「実証する項目」「要件」「示すこと」「示さないこと」「破れたときの害」「有限にした範囲」「扱わない領域」) | `<名前>.claims.md` |
| 台帳の見出しと行(「台帳」「閉じる前のチェック」「対象」「段なし:」「突き合わせ:」「実ログの spec:」「テスト対象:」「対象コード無し:」) | `tasks/` の各台帳 |
| ツールの出力の目印(「不一致:」「破れた規則」「検査されなかった規則:」) | 検証のツールの出力 |

この表は代表だけを挙げている。変える前に、その文字列を `git grep` で探し、読む側のコード(`loopeng/lib/hymme/`、`loopeng/bin/`、`hooks/`)をすべて確かめる。

`hymme chart draw` が書く `<名前>.chart.md` は、全文のハッシュで承認と照合する。見出しなどの生成する文字列を変えると、描き直したときに承認の取り直しが要る。

スキルの `description` にある、ユーザーの言い回しの例(「実物で確かめて」など)は、古い言い方も残す。ユーザーが口にする語は、この文書では決められない。

## 表記

- 常体と敬体は、そのファイルの今の書き方に合わせる。
- コマンド、ファイル名、識別子はバッククォートで囲む。
